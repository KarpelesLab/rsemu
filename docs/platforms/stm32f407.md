# STM32F407 — the `stm32f407` machine

Consumed by: `machines/stm32f407.machine`, `src/dev/stm32/`, `src/cpu/arm/v7m`.

The part modelled is an **STM32F407VGT6**: LQFP100, Cortex-M4 at 168 MHz, 1 MiB
of flash, 112 + 16 KiB of SRAM and 64 KiB of core-coupled memory. It is the
microcontroller on ST's own STM32F4 Discovery board, which is why the machine
file talks about LEDs on PD12–PD15 and a console on USART2.

A real part rather than a synthesis, because a microcontroller's memory map,
vector table and reset values are the part's and not the architecture's, and a
board file that averages several parts is one that matches none of them.

## How an interrupt is wired

This is the thing the board exists to settle, because it is different from every
other machine in the tree.

**The NVIC is inside the core.** Its enable, pending and priority registers are
part of the Cortex-M's own system block at `0xE000E000`, and external interrupt
*n* is exception number *n + 16*. There is no controller object between a
peripheral and the CPU, so a peripheral drives the core's pin `irq{n}` directly:

```
wire usart2.irq -> cpu.irq38
```

`cpu.arm.v7m` publishes `irq0` … `irq239`, plus `nmi` and `reset`. It drives no
output pin.

**The number belongs in the machine file.** 38 is USART2's position in RM0090
Table 62 — a fact about *this part*, not about ARMv7-M and not about a USART, and
the same USART model on an H7 sits at a different number. A device model that
contained one would be a device model that only worked on one chip.

A peripheral therefore needs no interrupt property and no controller handle: it
drives one output pin called `irq` and the board decides where that lands.

## What is not modelled, stated plainly

- **RCC drives no clock domain.** `st.rcc` computes `SYSCLK`, `HCLK`, `PCLK1`,
  `PCLK2`, the timer clocks and `RTCCLK` as exact rationals and publishes them,
  and it answers every poll a startup sequence makes: `HSEON` produces `HSERDY`,
  `PLLON` produces `PLLRDY`, and `CFGR.SW` is refused while the source it names
  is not ready. What it does not do is *re-rate* the scheduler's domains, so a
  guest that reprograms the PLL changes what RCC reports and changes no rate.
  `core::clock` can re-rate a domain; no seam reaches it from a device yet.
- **Nothing consumes RCC's clock gates.** Every `xxENR` and `xxRSTR` bit is a
  real output pin and no peripheral class has an enable input to wire it to, so
  a peripheral whose clock the guest never enables still works. The machine file
  shows this by having no `wire rcc.apb1en…` lines rather than by hiding it.
- **The FPU is a `part` choice, and this board takes it.** `part = "cortex-m4f"`
  is FPv4-SP-D16, which is what an F407 has and what firmware built
  `-mfloat-abi=hard` needs from its first function call — GCC uses `s0`–`s31` as
  scratch even in code that computes no floats. Double precision is not
  implemented at all: an F407 has none either, so nothing is lost.
  `part = "cortex-m4"` models the same silicon with the option left out —
  `CPACR` reads zero, `MVFR0` reads zero, a `VMOV` is a NOCP UsageFault — and is
  what this board said before the unit landed.
- **A DMA controller's view of memory is one space, not one per master.** The
  board has two spaces: `mem`, which is the core's, and `dmabus`, which is what
  `dma1` and `dma2` master. CCM is in the first and not the second, which is the
  distinction that costs a driver author an afternoon (RM0090 §2.1). The real
  bus matrix is finer than that — DMA1's memory port and DMA2's differ over
  flash and over which buses they reach — and modelling it means a space per
  master, which this board does not do.
- **No peripheral drives a DMA request.** `st.usart` and `st.i2c` publish no
  request output, so the two controllers serve memory-to-memory transfers and
  software-armed streams. RM0090 Table 43's request matrix is a fact about the
  part and belongs in the machine file, exactly as a vector number does; it goes
  in when there is a peripheral that can drive one.
- **EXTI lines 16–22 are undriven.** They are the peripheral wakeups — PVD, the
  RTC alarm, the OTG and Ethernet cores — and none of those is on this board
  (`st.pwr` publishes no PVD output). `SWIER` still raises them.
- **An advanced timer publishes two of its four vectors.** `st.tim` has `irq-up`
  and `irq-cc`; it has no break input and no commutation event, so Table 62's
  positions 24 and 26 are driven by TIM9 and TIM11 alone, and 43 and 45 by TIM12
  and TIM14 alone.
- **A watchdog reset resets the core, not the board.** `cpu.reset` is narrower
  than the part's `NRST`, which clears every block on the die; widening it needs
  a machine-level reset sink that does not exist yet. The cause still reaches
  `RCC_CSR`, because each watchdog's pulse is wired both to the core and to
  RCC's matching cause pin.
- **The BOOT pins are not modelled.** Flash is mapped at `0x08000000` and aliased
  at zero, which is the BOOT0-low case and the overwhelmingly common one.
- **A USART has no TX or RX pin.** Its data path is the character seam in
  `host::chardev` — a byte at a time to a terminal, not a bit stream on a wire.
  Firmware still configures `MODER` and `AFR` for its pins and the GPIO models
  that faithfully; it simply is not what carries the data. The GPIO's `af{n}`
  inputs exist for peripherals whose pin genuinely is a level.
- **`AFR` selects nothing.** The nibble is stored and reads back, so firmware
  configures normally, but a pin has one alternate-function input rather than
  sixteen. A board wiring two peripherals to one pin would need the selection
  honoured.
- **`OTYPER`, `OSPEEDR`, `PUPDR` and `BRR` are stored and reported and change no
  behaviour.** Open-drain, slew rate, pull resistors and baud rate are analogue
  or timing properties of a net this model does not have; `Usart::baud_divisor`
  reports the programmed divisor so a board that cares can act on it.
- **Everything else on the die.** SPI, I2C2 and I2C3, SDMMC, the OTG cores, the
  ADCs, the DAC, CAN, the RTC, the FSMC and Ethernet are separate device classes
  and separate `object` lines. This board is the floor they get added to.

## What runs on it

`tests/stm32f407_wiring.rs` is the one that keeps the vector numbers honest. It
hand-assembles firmware with a **real vector table**, arms TIM2 (Table 62
position 28) and EXTI line 5 (position 23, the shared `EXTI9_5`), and has each
handler store its own `IPSR` — the exception number the core actually vectored
through, which is the position plus sixteen. A wire to the wrong `cpu.irq{n}`
still pends *an* interrupt and still runs *a* handler, so reading the number
back is the only assertion that catches it. The same file checks that an
`HSERDY` poll terminates, that every register block decodes where Table 1 puts
it, and that CCM is in `mem` and not in `dmabus`.

`tests/stm32f407_board.rs` hand-assembles a Thumb-2 program into the flash slot.
It resets out of the boot alias, makes PD12 and PD13 outputs, sets both with one
atomic `BSRR` write, pushes `Hi!\n` out of USART2 one character at a time while
spinning on `TXE` between them, clears PD13 with the reset half of the same
`BSRR`, and then reads `NVIC_ISPR1` out of the core's own system block to see
USART2's interrupt arrive on bit 6 — external interrupt 38 — through the one wire
the machine file draws.
