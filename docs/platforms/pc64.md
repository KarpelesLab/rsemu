# `pc64` — a PC with a long-mode processor and no firmware at all

Consumed by: [`machines/pc64.machine`](../../machines/pc64.machine) and
[`src/dev/linuxboot.rs`](../../src/dev/linuxboot.rs). The chips are the ones
[`pc-at.md`](pc-at.md) documents; nothing here re-describes them.

`pc-at` and [`q35`](q35.md) are boards for **firmware**: they have a ROM socket,
a video adapter and a disk, and what runs on them starts at `0xfffffff0` in real
mode. This is a board for a **kernel**. There is no firmware on it: the object
at the bottom of the machine file writes a `bzImage` into memory and enters it
at its own 32-bit entry point, which is the one interface a Linux kernel offers
to something that is not a BIOS.

That makes it the smallest machine that can answer `ROADMAP.md` phase 6b's real
question — *does the x86 core survive a modern kernel's early boot* — without
also being a test of a boot loader, a partition table and an option ROM.

## The device set

Eight objects, and each earns its place by something the kernel does.

| Object | Why it is there |
| --- | --- |
| `cpu.x86`, `variant = "x86-64"` | the point of the board |
| two `pc.pic` | somewhere for IRQ0 to land; the board stays in PIC mode |
| `pc.pit` | the tick, and `quick_pit_calibrate` |
| `pc.sysctl` | port 0x61, which that calibration gates counter 2 through |
| `pc.rtc` | the wall clock, read out of CMOS |
| `uart.ns16550` | the console — `console=ttyS0` is how a machine with no video adapter says anything |
| `x86.linuxboot` | the kernel, the zero page, the e820 map and the stub that enters them |

No APIC: with no ACPI tables and no MP table there is nothing to tell the kernel
how interrupts are routed, so it stays in PIC mode — and `CPUID`'s APIC bit
follows the *board* rather than the part (it is set only when a local controller
is wired to the core), so the two agree. No 8042, no video, no DMA controller,
no IDE, no PCI: each would be a second thing being tested.

## How a kernel is entered

[`src/dev/linuxboot.rs`](../../src/dev/linuxboot.rs) implements the Linux/x86
boot protocol's loader side. It is an ABI between a boot loader and an image
rather than an implementation, and every field was read out of a real `bzImage`
and cross-checked against `file(1)`'s independent parse of the same bytes — the
image is *data* being loaded, which is the black-box use `ROADMAP.md` §1 allows.
No kernel source was consulted.

```text
  0x00001000  the stub: real mode in, protected mode out, and its GDT
  0x00007000  boot_params — "the zero page", built from the image's own header
  0x00008000  the kernel command line
  0x00100000  the protected-mode kernel, at its own code32_start
  high        the initial ramdisk, as high as the header allows
  0xfffffff0  the `reset` region: jmp far 0000:1000
```

**The processor is not set up from outside.** A device may not reach into a core
and set `CR0`, and it does not have to: the state the 32-bit entry point asks
for is eleven instructions away, and executing them tests the core rather than
bypassing it. The same choice `riscv.boot` makes, for the same reason.

A 64-bit kernel entered this way brings itself the rest of the way — its
decompressor builds identity page tables, sets `CR4.PAE` and `EFER.LME`, enters
long mode, decompresses several megabytes and jumps to the 64-bit kernel — all
before it has printed a single character. Anything that reaches the first line
of output has already exercised most of what 6b added to the core.

### `nokaslr` is on the default command line, and it is not a preference

Address-space randomisation draws entropy partly from the 8254: it issues a
read-back command and spins until the **null-count** bit in the status byte goes
clear. That bit is set by a control-word write and cleared when a count is
actually loaded (Intel 8254 data sheet, "Read-Back Command"), so on a machine
where nothing has ever programmed counter 0 it never clears — and there is no
firmware on this board to have programmed it. A kernel that randomises therefore
spins in the decompressor forever, before printing anything.

Both halves of that are correct behaviour. The combination is what a board with
no BIOS produces, and it is the kind of thing only a real guest finds.

## Userspace, and the two things that were in the way

The board now reaches a **shell prompt that echoes what is typed at it**:

```text
[  488.441711] Run /init as init process

rsemu initramfs on Linux 6.6.67-gentoo-x86_64 x86_64
/bin/sh: can't access tty; job control turned off
rsemu# ^[[6nuname -srm
Linux 6.6.67-gentoo-x86_64 x86_64
```

The last two lines are the only ones on this page that came back *in* rather
than out: `uname -srm` was fed to the 16550's receiver by the test's
`RSEMU_KERNEL_INPUT` script, and the guest echoed it and answered it. Nothing
before that had exercised the receive half of the UART at all. The `^[[6n`
between the prompt and the echo is the shell asking the terminal where the
cursor is; it is left in rather than tidied away, because everything on this
page is what the guest actually wrote.

Getting there needed two things, and neither was a defect in the board.

**A root.** There is no disk here and there is no PCI, so an initramfs is not
the cheap option, it is the only one: `nvme`, `ahci` and `virtio.blk` are all
PCI devices with no host bridge to sit behind, `pc.ide` would decode at
`0x1f0` happily enough — and the guest would never look, because a
distribution kernel builds `libata` and `virtio_mmio` as *modules* and the
modules live on the root that is not mounted yet. The kernel's own log settles
it: `PCI: System does not support PCI`, `SCSI subsystem initialized`, and no
storage driver of any kind registering. `scripts/fetch-testdata.sh
initramfs-x86` therefore builds one, around busybox, exactly as the
`initramfs` target does for `riscv-virt`.

**Time.** The kernel's crypto self-tests are hundreds of guest-seconds of
arithmetic between `Loading compiled-in X.509 certificates` and
`Freeing unused kernel image`, and they are what a nine-hundred-second run was
spending itself on. `cryptomgr.notests` on the command line removes them
outright. It is a *guest* choice rather than a board one, so it stays out of
`machines/pc64.machine`'s default `cmdline` — the board describes hardware —
and lives in the command below instead.

```text
scripts/fetch-testdata.sh initramfs-x86

RSEMU_KERNEL=/boot/vmlinuz \
RSEMU_INITRD=testdata/x86/initramfs-x86.cpio \
RSEMU_KERNEL_CMDLINE='console=ttyS0,115200 nokaslr cryptomgr.notests' \
RSEMU_KERNEL_MS=1200000 \
RSEMU_KERNEL_INPUT='rsemu# =>uname -srm\n' \
RSEMU_KERNEL_STOP_AT=x86_64 \
    cargo test --release --features machine-pc64 --test pc64_linux -- --nocapture
```

### What it costs

Measured on one host, release build, interpreter, and the ratio is the part
that travels:

| Run | Virtual | Wall | Where it ended |
| --- | --- | --- | --- |
| board default, no initramfs | 900 s | 236 s | inside the crypto self-tests, still making progress |
| initramfs + `cryptomgr.notests` | 931 s | 254 s | a shell prompt, `uname` answered |
| the same, built with `jit-x86` | 931 s | 255 s | the same, byte for byte |

Those three rows predate the translation-buffer split described next, so their
virtual-time figures are about 1.7% high against a build from today. They are
left as recorded rather than adjusted by arithmetic — a number in this table is
a run someone made.

**Virtual time runs about 3.7× faster than wall-clock time here, not 1:1.**
Roughly 250 virtual seconds of that is the decompressor, which is solid
computation and closer to 2.8×; the rest of the boot spends much of itself
halted between timer interrupts, and the scheduler does not pay wall-clock time
for virtual time nothing is running in. This page previously implied about
1:1, which is worth correcting rather than repeating: the number depends on
the host, on how much of the boot is idle, and on how much of it is
decompression, so it is a thing to measure per run and not a constant.

### What splitting the translation buffer moved

`cpu::x86::paging::Tlb` used to be one 32-entry array indexed `page % 32`,
shared by instruction fetches and data accesses. That is a 386's and a 486's
organization and those parts keep it; it is not what anything since the
Pentium has, and this board's `variant = "x86-64"` now gets the split pair —
a 32-entry instruction buffer and a 64-entry data one — that the P5 introduced.
The effect is entirely in the cycle column: a data operand can no longer throw
the code page's translation out, so the fetch that follows it no longer pays
for a re-walk.

Re-measured on this board, same host, same 12 718 592-byte 6.6 distribution
kernel, no initramfs, `cryptomgr.notests`, stopped at the guest's own
`Kernel panic` line so both runs end at the same instant in the guest's life:

| | Virtual time at the panic | The guest's own view of the machine |
| --- | --- | --- |
| one buffer | 700 349 ms | `tsc: Detected 25.647 MHz`, `lpj=85490` |
| two buffers | 688 228 ms | `tsc: Detected 25.779 MHz`, `lpj=85930` |

**−12 121 virtual milliseconds, 1.73%**, and the second column is the same
fact from inside: the kernel calibrates itself against the PIT, finds it is
getting 0.51% more work done per timer tick, and writes a bigger `loops_per_jiffy`
into its delay loop. Every other line of the 435-line console log is
byte-identical apart from the printk timestamps and the RTC readings that
follow from them — the guest does not *behave* differently, it is timed
differently.

Wall clock says nothing useful at this resolution and is not quoted as a
result: three post-split runs on this host took 197 s, 216 s and 236 s, a
pre-split run on a quiet host took 185 s and another under the same load as the
post-split ones took 239 s. Unrelated work held the load average between 8 and
24 throughout, which is a spread an order of magnitude wider than the effect.
The virtual-time figures, by contrast, reproduced to the millisecond across
every run of each build — 700 349 twice, 688 228 three times — which is the
determinism claim doing its job rather than a coincidence.

Nothing unpaged moved, and that is structural rather than lucky: every caller
of `Exec::translate` and `Exec::fetch_at` checks `Sys::paging` first, so with
`CR0.PG` clear the buffers are never consulted at all. `pc-at`, `pc-apic` and
`cpu::x86::firmware` are unchanged to the clock. `tests/goldens/frame-hashes.txt`
holds no x86 workload, so no golden was in a position to move either.

## What this found in the core

Six, and the first four each produced a guest that stopped dead with **nothing
printed at all** — which is what makes a board like this worth having. A unit
test cannot ask the question "does the whole of early boot work"; only early
boot can. The fifth needed userspace to find, and said so out loud. All six are
closed, as is the MTRR finding below them.

1. **`IA32_MISC_ENABLE` (`0x1a0`) raised `#GP`.** The decompressor's processor
   check clears the execute-disable lock through it *before there is an
   interrupt descriptor table*, so the fault was a triple fault forty
   instructions in.
2. **A null selector loaded into `SS` raised `#GP` in 64-bit mode.** It is legal
   there below ring 3 (*Intel SDM* volume 3 §5.4.1), and the first thing a
   64-bit kernel does after its long jump is load all six segment registers with
   zero.
3. **`MOV r64, CR2` transferred thirty-two bits.** In 64-bit mode the operand
   size is 64 bits with no `REX.W` and a `66` prefix cannot narrow it. The
   kernel's early page-fault handler reads `CR2`, subtracts `PAGE_OFFSET`, and
   decides the address is out of range when the top half is missing; it then
   declines to map the page, falls through to a handler with no fixup, and halts
   in a loop with no console.
4. **`POP` to memory addressed its destination before the increment.** *Intel
   SDM* volume 2, `POP`: the effective address is computed *after* `RSP` moves.
   `pushf` / `pop 0x10(%rsp)` is how a compiler writes `local_irq_save` on
   x86-64, so the flags landed eight bytes low, on top of a live local. The
   kernel lost a function argument that way in `text_poke` — the routine that
   rewrites its own code — and died with a null-pointer dereference sixteen
   instructions later, thirty-two seconds in.
5. **The packed-integer half of SSE2 is not decoded, and `CPUID` says it is.**
   This one is the first thing *userspace* found, and it found it immediately:

   ```text
   [  490.348390] Run /init as init process
   [  490.575039] traps: init[1] trap invalid opcode ip:4a80b6 sp:7fff8accf530 error:0 in busybox[401000+18c000]
   [  490.597064] Kernel panic - not syncing: Attempted to kill init! exitcode=0x00000004
   ```

   The bytes at that address, from the kernel's own `Code:` line, are
   `66 0f 6e ca` — `MOVD xmm1, edx`, which the core has — followed by
   `66 0f 62 c8`, which is `PUNPCKLDQ xmm1, xmm0` (*Intel SDM* volume 2,
   `PUNPCKLBW/PUNPCKLWD/PUNPCKLDQ/PUNPCKLQDQ`), which it does not. That is
   glibc's static startup packing two `CPUID` results into one XMM register,
   about a hundred instructions into the first user-mode program on the
   machine.

   `src/cpu/x86/isa.rs`'s `SECONDARY_66` table carried the packed-*double*
   half of SSE2 in full and, of the packed-integer half, only `MOVD`, `MOVDQA`,
   `MOVQ`, `PAND`, `PANDN`, `POR` and `PXOR`. Everything from `66 0F 60` to
   `66 0F 76` — the unpacks, the packs, `PSHUFD`, the shift group and the
   compares — and the whole `66 0F D4`-`66 0F FE` arithmetic block were absent,
   while `CPUID.01H:EDX[26]` is set for `variant = "x86-64"`. A guest that
   believes `CPUID` is entitled to all of them.

   **Closed.** The sixty-two encodings are in the table, in the three shift
   groups Intel numbers 12, 13 and 14, and in the `F3`/`F2` maps for the two
   half-register word shuffles — gated on `Features::sse2` rather than turned
   on unconditionally, so a part configured without the bit still raises `#UD`
   for every one of them and `CPUID` and the decoder keep saying the same
   thing. The interpreter executes them in `fpexec::sse_packed`; there is no
   MMX form of any of them, because there are no MMX registers here.

   The fixture still fetches busybox.net's statically linked **musl** build,
   because that is what the script downloads; the glibc path is what this
   finding was about and the encodings it stopped on now decode, but a
   glibc-linked userspace has not been run end to end on this board since.
6. The reserved-NOP space (`0F 18`-`0F 1F`) was missing, which is `#UD` on the
   first `ENDBR64` of a kernel built with indirect-branch tracking.

### And one that is the board rather than the core

With `CONFIG_DEBUG_VM_PGTABLE` on, the kernel warns twice during `init`:

```text
pmd_set_huge: Cannot satisfy [mem 0x00200000-0x00400000] with a huge-page mapping due to MTRR override.
WARNING: CPU: 0 PID: 1 at mm/debug_vm_pgtable.c:441 debug_vm_pgtable+0x1b50/0x1de0
```

The line above both of them was `MTRRs disabled (not available)`: the core did
not advertise `CPUID.01H:EDX.MTRR[12]` and answered `RDMSR 0xfe` with `#GP`, so
the kernel declined to install a 2 MiB mapping it could not prove was
write-back, and its own page-table self-test then warned that `pmd_set_huge`
returned zero. The boot continued and nothing else noticed.

It was a gap in the *preset* rather than in this board, and it is closed. Every
part that implements long mode also implements the memory-type range registers,
so `Features::mtrr` is part of `Features::X86_64` and `Features::validate`
now refuses a long-mode part without it. The core has `IA32_MTRRCAP`,
`IA32_MTRR_DEF_TYPE`, the eight variable base/mask pairs and all eleven fixed
ranges, with the reserved bits and the two undefined memory types refused
exactly as hardware refuses them — which is what lets a guest probe.

They are **stored and reported, not obeyed**, and `prot::mtrr` argues why that
is the whole truth rather than a shortcut: a memory type says what a cache may
do, this core has no cache, every access is one bus transaction in program
order, and that behaviour satisfies `UC` — which is a legal implementation of
every weaker type. No guest can construct an experiment that separates this
answer from a processor with its caches disabled. Add a cache model and the
registers stop being storage.

## The JIT, and what `engine = "jit"` is worth on this board

**It is a line you can write now.** `cpu.x86` takes `engine = "interp"`,
`engine = "jit"` — blocks lifted by `cpu::x86::lift` and executed through
`jit::Dispatcher`, with its block cache, its chained exits and its
self-modifying-code invalidation — and `engine = "jit-host"`, which is the same
with `jit::x86`'s host code generator underneath. `src/cpu/x86/engine.rs` is the
join, and it is `cpu::riscv::engine`'s shape because the claim is the same one.

`machines/pc64.machine` and `machines/q35-linux.machine` both declare it as a
`param`, so `rsemu run -p engine=jit-host` chooses it from the command line;
`RSEMU_ENGINE` on `tests/pc64_linux.rs` and `tests/q35_linux.rs` overrides what
the property said, and is what the tables below were measured with.

### What it is worth, measured

This board, a stock 12 718 592-byte Gentoo `6.6.67` `bzImage`, the busybox
initramfs `scripts/fetch-testdata.sh initramfs-x86` builds,
`cryptomgr.notests`, and **900 seconds of guest time** — which is well past
`Run /init as init process` at 467.8 s. Release build, one host, medians of
**three interleaved reps**: one run of each engine, in turn, round and round,
because the interpreter is the control and a control measured in a different
sitting is not one.

| `engine` | 900 s of guest time | 60 s of guest time (the decompressor) |
| --- | --- | --- |
| `interp` | 276.5 s | 16.7 s |
| `jit` | 184.3 s (1.50×) | 10.2 s (1.63×) |
| `jit-host` | **86.4 s (3.20×)** | **3.0 s (5.5×)** |

The same three on the tree this round started from, one rep each, interleaved
with each other in the same sitting on the same host: `interp` 302.1 s, `jit`
212.7 s (1.42×), `jit-host` 112.0 s (2.70×). So the whole of the improvement
below is **112.0 s to 86.4 s** on the same board and the same guest, and the
interpreted control moved by less than 9% between the two sittings.

Reps, in the order they ran: 301.8/275.9/276.5, 190.1/184.3/184.0 and
88.1/86.4/82.6 for the first column; 18.1/16.7/16.6, 10.2/10.3/10.2 and
3.1/2.9/3.0 for the second. The first interpreted rep is the outlier and it is
the host rather than the build — seven agents share this machine and its load
average moved between 14 and 36 over the hour these ran in, which is exactly
why the three engines are interleaved rather than measured in blocks.

The second column is the same board over the first sixty seconds of guest
time, which is *entirely* the kernel's own decompressor: several hundred
million instructions of straight-line integer arithmetic, all of it inside the
lifted subset even before this round. It is the best case, it is unchanged by
this round, and it is worth quoting beside the first — because the gap between
5.5× and 3.20× was, when these were taken, the whole of what the exclusions and
the boundary refusals cost on a real workload. It used to be the gap between
5.7× and 2.65×; the boundary refusals are gone now, and what would be left of
that gap is the exclusion list alone.

**All three engines produce byte-identical guest output** — 653 lines — and end
900 000 virtual milliseconds at the same `CS:RIP`, `CR2`, `CR3`, `CR4`, `EFER`
and flags, from the same translations. The only lines that differ between the
three logs are the test harness's own wall-clock ones.

**The wall-clock table above is the previous round's and was not re-measured to
the same standard**, deliberately: this host carried five other agents' builds
throughout, and the two rounds before this one both found the load could not be
separated from the effect. What *is* deterministic — the retired fraction, the
block counts, the translation counts — is re-measured below to the instruction,
and the host instruction counts are taken under callgrind, which does not care
about load.

One rep of each engine did run in one sitting on this round's tree, and it is
worth quoting only because the **control barely moved**: `interp` 278.6 s
against the table's 276.5 (+0.8%), `jit` 191.5 against 184.3 (+3.9%), and
`jit-host` **67.6 s against 86.4 (−21.8%)**. One rep is not a median of three;
an interpreted control within a percent of its own median is what makes the
third row worth reading at all.

### The honest headline is the block fraction, not the speedup

Over that 900 seconds the guest retires 1 797 272 974 instructions, and
**1 785 024 342 of them — 99.3% — retire inside a translated block.** It was
97.3% before this round and 84.5% two rounds before that, measured the same way
on the same host and the same guest.

The rest of the counters say what the runtime did with them: **364 481 972
blocks executed from 132 053 translations**, 311 713 835 of them (86%) reached
by following a patched exit with no lookup at all, and **49 932 thrown away
because the guest wrote into the page they came from** — a kernel really does
patch its own text, and on x86 honouring that is architectural rather than
optional.

The translation count nearly halved and that is the guard leaving rather than
the cache improving: a block refused on the budget was lifted, measured,
reported untranslatable and thrown away, so it was counted and then had to be
lifted again next time.

Under `jit-host` every one of those block executions was compiled host code:
`jit::x86` refused nothing this guest produced.

(The denominator is a *statistic* rather than the guest's exact instruction
count, and the two rounds differ by seven in it: an instruction that faults is
counted by `interpret` and is not counted by a block, which retires everything
before it and nothing after. Seven in 1.8 billion.)

### The slot-read hoist, wired in and then measured rather than assumed

`ir::hoist_slot_reads` landed with the **A64** frontend and was wired into that
one alone, though nothing in it is A64-specific. All three frontends emit a
guest register's first read one or two instructions after that instruction's
boundary, and that is exactly what turns `jit::x86`'s per-*region* replay of
deferred charges and boundaries back into a per-*instruction* one; the pass
moves each read to the top of its region, where a run of them collapses to one
replay point or to none.

`cpu::x86::lift` now calls it, next to the dead-code elimination it already
ran. What that is worth on this board, twenty guest seconds of the same
`bzImage` under `engine = "jit-host"`, callgrind with `--cache-sim=no`:

| | before | after |
| --- | --- | --- |
| host instructions | 28 567 216 644 | **27 832 228 449** (−2.57%) |

Both runs end on the same `Machine::state_hash`, so the two columns are the
same guest work. **The number does not match A64's −4.74% and was not expected
to**: what the pass can remove is bounded by how many boundaries a read is able
to move above, which is bounded by how long a block is, and a block on this
board retires 4.79 guest instructions against A64's 6.44. `cpu::riscv::lift`
got the same treatment in the same round and −0.73% at 3.18 instructions per
block, which is the same ordering.

### Where the other 48 666 616 used to go, and it was not where the list said

*(The two sections that follow profile the **previous** round's 48.7 M. They
are kept because they are what chose this round's work: three quarters of that
number was one mechanism, and the section after them is that mechanism being
removed.)*

The exclusion list this page used to print — *"the string primitives and
`REP`, `DIV`/`IDIV`, `LOCK`, `PUSHF`/`POPF`, the segment loads, `SYSCALL`,
`SWAPGS`, `WRMSR`, x87 and SSE"* — was a list of what `cpu::x86::lift` refuses,
not a measurement of what refusing them costs. Instrumenting the interpreter to
count what it actually took, by opcode, split the 223.6 M two ways and neither
half was the list:

| | before | after | share of the guest |
| --- | --- | --- | --- |
| encodings outside the lifted subset | 105.2 M | **11.9 M** | 0.66% |
| inside it, refused at a boundary | 174.1 M | **36.6 M** | 2.04% |

**The second row was the larger one and it is not an exclusion at all.** It is
almost entirely the budget guard: a block runs only when its worst case fits
what is left of the caller's quantum, an unknown block's worst case was
`worst_bound` — ten times what a block really costs — and the measurement that
would have contradicted it only happens *inside a lift that never ran*. A PC
first reached in the tail of a quantum therefore stayed on the interpreter for
the rest of the boot. `cpu::x86::engine`'s module documentation has the repair.

And the first row was three encodings, not ten:

| refused | before | after |
| --- | --- | --- |
| the reserved-NOP space (`0F 1F` and friends) | 41.5 M | 0 |
| `RET` — the computed near transfer, long mode only | 34.2 M | 0 |
| `PAUSE` and `ENDBR64`, which carry a repeat prefix | 17.7 M | 0 |
| everything else | 11.8 M | 11.9 M |

`0F 1F /0` is the multi-byte `NOP` a compiler pads with and `ENDBR64` begins
every function of a kernel built with indirect-branch tracking, so the two of
them are a fixed fraction of any 64-bit text; `RET` is simply what a function
return is. Together they were **88.7%** of everything the frontend was handing
back, and closing them left a tail whose largest member is `CMPXCHG` at 1.6 M —
0.09% of the guest's instructions.

The list's own headline items are measured too, and they are small: **the
string primitives are 0.15 M**, because `REP MOVSB` retires as *one* guest
instruction however many bytes it moves — a real cost in time and almost none
in this metric. `DIV`/`IDIV` are 0.97 M, x87 and SSE together 1.2 M, every
`LOCK`-prefixed instruction 0.21 M, and `SYSCALL`, `SYSRET`, `SWAPGS` and
`WRMSR` together fewer than **2 000** in nine hundred guest seconds.

### Why a better bound does not close it

A block runs only when its **worst case** fits what is left of the quantum, and
`engine::block_bound` is that worst case: every `CHARGE` in the block plus 48
ticks for each data access — two page-table walks and eight one-byte bus
transactions, which is what an eight-byte access crossing a page boundary
really costs under a four-level walk. A real access is usually two ticks. So
the obvious repair is a tighter bound, and the same run measured what one would
buy before anybody wrote it:

| | |
| --- | ---: |
| blocks admitted | 289 855 915 |
| mean bound of an **admitted** block | **185** |
| boundaries refused on the budget | 69 941 067 |
| mean ticks left at a refusal | 827 |
| mean bound of a **refused** block | **1 636** |
| refusals a **per-width** bound would admit | 2 770 055 (4.0%) |
| refusals a **buffer-hit** bound would admit | 18 689 219 (26.7%) |

The refusals are not ordinary blocks caught in the tail of a quantum. They are a
small population of *fat* ones, bounded nine times higher than the blocks that
run. Charging each access at its own width — a one-byte access cannot cross a
page, so it walks once and makes one transaction — is sound and admits **4.0%**
of them, which is 0.08% of the guest. The floor no static bound can go below, a
buffer hit and one aligned transaction, is *unsound* and admits **26.7%**,
which is 0.54%. Neither is worth the code, and the second is not available at
any price.

### What closed it

A block needs a bound only because a block cannot stop in the middle. Give it a
**tick allowance it may leave at an `insn_start` boundary** and the guard has
nothing left to decide: run instructions until the allowance is spent, stop at
the next boundary — which is exactly what the interpreter does, so the two
cannot disagree about where they stopped.

That was an `ir`/`jit` seam rather than a frontend one, and it exists now.
`IrHost::spent` is asked by `ir::Interp` and by `jit::x86`'s
deferred-bookkeeping replay at every guest instruction boundary but a block's
first and an exit, and by `jit::dispatch` at every block boundary but a run's
first; a `true` publishes that boundary's live map exactly as a fault does and
stops with `Outcome::Spent`. `cpu::x86::engine` carries the allowance `advance`
was handed and answers `Exec::used >= allowance`. `worst_bound`, `block_bound`,
the cost half of the `(pc, key)` table, the late guard inside
`Lifter::translate` and the `measure` that read a cached block's cost are all
deleted; what is left of the table is the negative half, which says *there is
no block at this PC* and saves a lift that would fail at its first instruction.

**And x86 pays for it in the frontend.** `lift::Flags::Elide` leaves out of a
boundary's live map the arithmetic flags the instruction it begins is about to
write, and dead-code elimination then deletes the arithmetic behind them. That
is sound for a block that runs to its terminator and sound at a fault — elision
is refused wherever an instruction can take one — and it is **not** sound for a
block that *leaves*, because the guest resumes standing at that boundary with an
interrupt able to push a stale `EFLAGS`. So `engine::FLAGS` is `Flags::Eager`.
`cpu::riscv::engine` adopts the same seam and needs no frontend change: its
lifter elides nothing, because `live_regs()` names every bound slot.

Priced under callgrind — host instruction counts, which do not care what else
is running on the machine — over 120 guest seconds of the same board, the same
binary built three ways:

| --- | ---: | ---: |
| the guard, `Flags::Elide` (the tree this round started from) | 122 485 018 912 | — |
| the guard, `Flags::Eager` | 125 610 898 037 | **+2.55%** |
| the allowance, `Flags::Eager` (shipping) | 113 970 389 647 | **−9.27%** |

Net **−6.95%** of host instructions. The wall clock was not re-measured: five

### What was in the way, and what each turned out to be

1. ~~**No CPU core has a JIT execution path.**~~ **`cpu::x86::engine` is
   that path**, and four things x86 needed that `cpu::riscv::engine` did not:

   * **The open bus is architectural state and a block makes no fetches.**
     `State::open_bus` is in the snapshot, so it is in `Machine::state_hash`,
     and the interpreter latches a byte on every bus cycle including the one it
     spends fetching each instruction byte. The rule, read off
     `Exec::instruction`: after guest instruction *i* the open bus holds the top
     byte of *i*'s last data access if it drove one, and the last byte of *i*'s
     own encoding otherwise. `engine::close_bus` puts the second case back, and
     the length it needs is free — `InsnStart::next_pc` is the instruction's own
     successor even for a taken branch, so `next_pc - pc` is the encoding length
     and an exit boundary is the one where they are equal. Whether the
     instruction drove the bus is read off `Exec::used` rather than off "it made
     an access", because a segment-limit violation is checked before anything is
     charged and so puts nothing on the bus at all.
   * **Every write this core makes is collected in one place.**
     `Exec::phys_write` accumulates the guest-physical pages it wrote, so a
     compiled block's store, an interpreted `REP MOVSB`, an exception's stack
     frame and a page-table walk's accessed-bit write-back all reach the block
     cache through one funnel. That is strictly more than the IR can see, and on
     x86 it has to be: most of what writes code is outside the lifted subset.
   * **A block below long mode assumes the upper halves are clean.**
     `lift::Lifter::read_reg` reads a 32-bit operand as *the whole slot* there —
     "below long mode it **is** the doubleword" — while `Regs::dword` truncates.
     The two agree exactly while bits 32-63 of every general register are zero,
     which is true from reset and stays true because `Regs::set_dword`
     zero-extends… and is **not** true in compatibility mode, where a 64-bit
     kernel's leftovers are still in the file when a 32-bit code segment starts
     executing. `engine::narrow_state_is_clean` checks it, program counter
     included. It was an unstated precondition of the frontend, and the
     differential harness could not have found it: `Case::start_regs` narrows
     its register file deliberately.
   * **The world needed a counter and nothing kept one.** `lift::key` folds
     `World::generation` into the cache key under `Origin::Flat`;
     `engine::Boundary::world_of` bumps it by comparing the world it derived
     against the last one. Under paging it is not in the key at all — the
     physical address the entry translation resolved to names the block — which
     is why `SWAPGS` moving `GS.base` on every kernel entry moves no key.

   One number decided a constant, *while the guard existed*: the frontend was
   asked for **sixteen** instructions a block here rather than
   `lift::MAX_INSNS`'s sixty-four, because a cold block's worst case under
   four-level paging is 206 ticks an instruction (fifteen fetch bytes at two
   clocks, `IMUL`'s eighty, and two page-crossing eight-byte accesses at two
   walks each), so sixty-four would have bounded it at 13 200 — above
   `SchedulerConfig::max_ticks_per_quantum`, which is 10 000, and **no block
   would ever have been admitted**. Nothing computes that bound any more and the
   test that asserted it went with it; "The knob the guard chose" above is where
   the constant is decided now.

   What is deliberately *not* there: an inlined load path. `jit::FastMem` is
   what RISC-V publishes a `LoadPlan` through, and x86 cannot — a load's address
   is an *effective* address, so the segment base is added and the limit checked
   before anything could reach a table, and `jit::x86`'s `Compiler::inlinable`
   refuses a segmented access for the same reason. Every x86 `MemOp` carries a
   `SegId`. It is worth setting beside `riscv-virt`'s 2.28× rather than
   comparing the two boards' numbers as if they measured one thing: RISC-V
   serves 97.3% of its compiled loads inline and gets nothing like x86's work
   per block, and this board serves none of its loads inline and gets a great
   deal. Lowering the segment fold into generated code is what would close the
   gap, and it is a frontend change rather than a wiring one.

2. ~~**The x86 frontend refuses this guest.**~~ **It does not any more.**
   `lift::World::of` accepts a core in long mode, and
   `tests/x86_lift_differential.rs` runs a generated corpus there under all six
   shape-and-flag frontends, through one freshly lifted block, through the
   block cache, and — where the host has the backend — as compiled host code.
   Getting there took paging first, which was a prerequisite rather than an
   alternative: `Origin::Paged` is in the subset on a part whose instruction
   and data translation buffers are separate
   (`cpu::x86::paging::Buffers::Split`, which is what `Variant::X86_64` has),
   and that took four things:

   * a block's **data** accesses go through the interpreter's own memory path —
     `Exec::read_mem` and `Exec::write_mem`, the functions `Exec::step` calls —
     so the walk, its tick cost, the accessed and dirty bits and the
     page-crossing split are one implementation rather than two;
   * the self-modifying-code guard is **not** made to compare physical pages;
     it compares linear ones, two of which may alias one physical page, so
     `lift` refuses `Smc::Guard` under paging and `Smc::EndBlock` was the
     policy — the same answer `cpu::riscv::lift` gives, with both ends of the
     invalidation physical: `Lifted::page` is the page the entry resolved to
     and the host notes the physical address its store reached. **That is the
     one of the four that has since been replaced**, by `Smc::HostGuard`:
     `Host::note_writes` makes the comparison the IR could not, on the
     guest-physical page at both ends, so a store is an ordinary instruction
     under paging too. "Where the host instructions go" below is what it was
     worth;
   * `Block::key` carries **the physical address the entry translation
     resolved to** rather than a `CR3` generation, because `cpu::riscv::engine`
     measured a generation being unusable on a real guest — Linux bumps its
     counter on every `SRET` and the cache missed every time. The address and
     not its page: a `CS` base moved by a page would otherwise give the same
     `EIP` a different offset in the same frame under one key;
   * the caller reads the entry page through the **fetch** path, on every
     execution of every block, through `Frontend::enter`. Getting that wrong is
     the failure mode that looks like a working JIT with a clock short by one
     walk per entry, and it is now a compared column: a paged case charges more
     ticks than the same program unpaged, and the two engines agree on the
     number.

   Long mode is the layer above that, and it is not optional for this board:
   a processor cannot be in long mode with paging off — `EFER.LMA` is set only
   when `CR0.PG` goes on with `EFER.LME`, and IA-32e paging requires `CR4.PAE`
   (*Intel SDM* volume 3 §9.8.5) — so the walk here is four levels of
   eight-byte entries rather than two of four. What it took, item by item
   against the list this page carried last round:

   * **`REX` and sixteen registers.** The slot numbering is sixteen general
     registers, the program counter and the seven flag slots, in **both**
     worlds rather than eight that become sixteen: the numbering is the
     frontend's private contract with its host, nothing else reads it — in
     particular not the snapshot, which `cpu::x86`'s `save`/`load` and
     `host::gdb::arch` own and which this change does not touch — and one
     numbering that always holds is cheaper than two that must agree. `REX`
     also decides what a byte-sized register number four *means*, `SPL` rather
     than `AH`, which `Regs::read` takes a flag for and the lifter now does too.
   * **`MULU2`/`MULS2`.** A 64-bit `MUL` or `IMUL` lowers to the double-width
     multiply the IR op list carries and that a 32-bit subset never reached.
     `IMUL`'s "does the product fit" test follows it: with the halves in hand
     the question is whether the high half is the low half's sign fill, which
     is the only form of it that can be asked when the product is 128 bits and
     no temporary holds one.
   * **`RIP`-relative addressing.** Both halves are lift-time constants, so the
     whole address is one; the effective-address helper's thirty-two-bit mask
     became `World::addr_mask`, which is the identity at sixty-four bits.
   * **`SHL`'s carry, which was not on the list.** The same hole the carry of
     `ADD` had and one function further along: it was bit `bits` of the
     unmasked product, and at a 64-bit operand that bit does not exist. It now
     comes off the source as bit `64 - n`.
   * ~~**A computed near transfer, which long mode *removes* from the
     subset.**~~ **Closed, and it was the second-largest thing this frontend
     refused: 34.2 M instructions in nine hundred guest seconds, because a
     function return is the commonest computed transfer there is.** `RET`,
     `JMP r/m` and `CALL r/m` fault with `#GP(0)` on a non-canonical target —
     an exception at the transfer with the pre-instruction state restored.

     The answer written here last round — *"a side exit taken before any state
     is bound"* — is wrong, and it is wrong on the **clock** rather than on the
     state. A side exit restarts the instruction, so its fetch, its operand
     read and its static charge are paid twice; rolling those back is worse,
     because the operand read filled a translation buffer and may have written
     an accessed bit, so the interpreter's second attempt would be *cheaper*
     than a first; and it cannot be rolled back at all without also restoring
     `State::open_bus`, which the read latched and which is in the snapshot.

     What works is not leaving. The block **delivers the fault where it
     happens**, at the transfer's own boundary — whose live map is by
     construction the pre-instruction state, which is exactly what
     `Exec::step`'s own roll-back produces — and `cpu::x86::engine` vectors it
     through `Exec::deliver` without re-executing anything. `lift::TRANSFER` is
     how a block says so: the target is checked as the `AccessKind::Fetch` it
     architecturally is, in an address space nothing is stored in, which the
     host answers by testing the address and touching no memory. It is the one
     seam `IrHost` offers for raising a guest exception, because its load and
     its store are the only methods that can fail.

   The harness moved with the frontend, because a wider world with the old
   corpus is an empty coverage claim. `differential::synthesize64` writes the
   encodings long mode actually has, the machine maps its four guest pages
   **twice** — once at `BASE` where the code runs and once at
   `differential::HIGH`, two and a half tebibytes up, where the corpus points
   its data — and both engines are compared over all sixteen registers at their
   full width. The high window is what makes the world testable rather than
   merely reachable: a machine whose whole address space fits below 2^32 cannot
   tell a correct 64-bit address computation from one that masks its answer,
   and a deliberately injected mask survived until the window moved. Sixteen
   bugs were injected into the new paths one at a time and fifteen were caught;
   the sixteenth is a shift left out of range at sixty-four bits, which both
   backends in the tree reduce modulo the width, so it is asserted by shape
   instead.

   So a 64-bit block lifts today, and it runs today.

   And the corpus moved again this round, for the same reason and with the same
   result. `synthesize` and `synthesize64` now generate the three computed near
   transfers, the reserved-NOP space, `PAUSE`, `ENDBR64`, `49 90` — which is
   `XCHG R8, RAX` and *not* a no-operation — and a **byte** shift by `CL`,
   which neither of them had: `D3` is the word and doubleword form and `C0` is
   the byte form with an immediate, so a byte destination and a count that may
   be zero had never met. Widening it found two live defects in code that was
   already shipping, both in long mode and neither reachable by the old draw:

   * a 32-bit shift or rotate by a `CL` that masks to **zero** wrote its
     operand back, and a doubleword write zero-extends — so `ror ecx, cl` with
     `CL` zero cleared the upper half of an `RCX` the instruction must not
     touch. `Exec::shift` returns before it even reads the operand there. The
     selection is now over the whole slot rather than over the operand, which
     has no width to be wrong at;
   * `90` with `REX.B` is `XCHG R8, RAX`, which the interpreter has performed
     all along while the frontend lifted it as a `NOP`. The encoding leaves the
     subset.

   Twenty-one bugs were then injected one at a time and **seventeen were
   caught**; the four survivors are argued in `cpu::x86::engine` and
   `cpu::x86::lift` rather than counted as coverage. The sweep itself found one
   more thing worth writing down: its first run filtered the two integration
   binaries out by accident — `cargo test --lib cpu::x86 --test x86_engines`
   applies the positional filter to *every* binary — so four mutations
   "survived" a suite that had never run the tests written to catch them. A
   mutation sweep whose harness is not itself checked measures the harness.

   And it moved once more, in the direction that round's two findings pointed:
   the corpus was audited against `cpu::x86::lift` for what it could *not*
   draw, because a form nobody generates is a path nobody compares and every
   sweep still passes. Fifty-six forms became ninety-eight and sixty-two became
   ninety-seven, adding **a 16-bit operand size** — a whole operand width the
   lifter has always had and neither corpus had ever written — the four high
   byte registers `AH`, `CH`, `DH` and `BH`, the entire SIB addressing arm
   (a scaled index, no index, and no base), the 32-bit displacement forms, the
   direct offsets and their `moffs64`, `MOVZX`/`MOVSX` from a word, the
   accumulator-immediate forms, group `80`, `PUSH imm`, `LEAVE`, `CALL rel`,
   `JMP rel` and the near `Jcc`. Two things fell out and neither is a lifter
   defect: **`CMOVcc` had never been generated in a 32-bit world at all**,
   because that sweep ran a 386 and `CMOVcc` is a property of the instance; and
   `synthesize64`'s byte shift pushed no immediate, so every draw of it
   swallowed the first byte of the instruction after it. Neither has a symptom
   a sweep can report, which is why the coverage claim is now checked **form by
   form** rather than in aggregate.

   A **fourth world** landed with it. Compatibility mode — `EFER.LMA` set, so
   the walk is IA-32e's four levels, under a *32-bit* code segment — is a world
   `World::of` has accepted all along, because it asks `Sys::sixty_four`, which
   is `LMA` **and** `CS.L`; nothing had ever put a case in it. It is what this
   board's own kernel is in whenever it runs a 32-bit program, and it is the
   state `engine::narrow_state_is_clean` was written for. It now runs the
   generated sweeps, the cached-and-chained sweep, the engine's own fixtures,
   the fuzz target, and `tests/x86_engines.rs`, where all three engines must
   hash to the same machine at every checkpoint in it.

The consequence for anyone hoping a Linux kernel is a big differential corpus:
it is one, and now for x86 too — as a *frontend* corpus and as an *engine*
corpus. `pc-at` and `q35` run 32-bit protected-mode firmware and this board runs
a 64-bit kernel; both are inside the lifted subset and both now reach a
dispatcher.

### A load from the APIC can raise `INTR` in the middle of a block

An instance of the class `docs/testing/long-run.md` records for A64 — *where a
quantum ends*, not what an instruction computes — found on this core and fixed
in `IrHost::load`. `cpu::riscv::engine` had the same defect from a different
device; `docs/platforms/riscv-virt.md` has that half.

`cpu::x86::engine`'s module docs enumerated what can raise an interrupt from
inside a block and concluded *"a store into an interrupt controller is the one
thing that can, and it is seen at the very next boundary"*. Both halves were
wrong. A **load** can raise one and was not looked at; and the store was only
the last instruction of its block under `Smc::EndBlock`, which `admit` picked
*under paging* — with paging off the policy was `Smc::Guard`, a store was an
ordinary instruction, and the block ran straight past it. (Under
`Smc::HostGuard` a store is an ordinary instruction in every world, so this is
now the *only* thing that answers it, in both.) The local APIC and the HPET
are **lazily advanced** (`ROADMAP.md` §4.2): `MemOps::read` catches the chip up
to this core's live position before it answers, and an APIC timer that reaches
zero inside that catch-up calls `State::request` for its vector and drives
`INTR` there and then.

Ordinarily that is a quantum boundary and invisible, because
`Scheduler::natural_target` ends a round on the soonest event a lazily-advanced
device has of its own. The window is a timer the guest **reprograms into the
round that is already running** — a write to the initial-count register, which
is what a tick handler does. The round's target was chosen when the round began
and does not move, so the next read of the current-count register (`0x390`), or
of the HPET's main counter, crosses the expiry. `INTR` rises between two
instructions of a lifted trace and the block runs on to its natural end, up to
`lift::MAX_INSNS` instructions past where `Exec::step` would have taken it.

There are two regression tests in `src/cpu/x86/engine.rs`, one per half:
`a_load_that_raises_intr_is_taken_where_the_interpreter_takes_it` and
`a_store_that_raises_intr_is_taken_where_the_interpreter_takes_it`. Each puts a
one-register device that asserts `INTR` when touched three instructions from
the end of a merged trace, in the unpaged world. With either check removed the
interpreter shuts down with `EAX = 0` and both translated engines with
`EAX = 19`.

The pin test itself is now one function, `engine::pins_pending`, asked by
`admit` before a block runs and by `IrHost::load` and `IrHost::store` from
inside one, so the three cannot drift. The *state* half of `admit`'s test — a
shutdown, a halt, a `HLT` waiting for a `SIPI`, the interrupt shadow, the trap
flag — stays where it was, because every one of them is written by an
instruction the frontend does not lift and so cannot move inside a block. It costs `IrHost::spent` nothing: `Host::hand_back` retires the
run's tick allowance rather than adding a second field to the comparison every
guest instruction boundary makes. Measured under callgrind — the host was too
busy for a clock — `X86::run_budget` taken inclusively over the whole of
`benches/x86_dispatch --smoke` went from 1 219 379 096 host instructions to
1 221 612 704, **+0.18%**, and x86 pays it on every access because it publishes
no inlined memory path.

`benches/x86_dispatch` grew a second table for this, in the shape
`benches/a64_dispatch` already had: the first table drives `Dispatcher` from a
host of its own and cannot see `cpu::x86::engine::Host` at all, so nothing in
it could have measured either the budget seam or this one. The new table runs
`X86::run_budget` across six quanta with `interp` as the control.

### The third way in was the entry translation, and "page tables live in DRAM" was not a defence

`admit` asks the pins and *then* charges the entry fetch translation, which on
a buffer miss is a **walk** — so a walk sits between the last look at the pins
and the block's first instruction. The engine's module docs used to close that
with *"on a PC that is empty — page tables live in DRAM"*, which is a statement
about what a guest does rather than about what the board or the core permits.
`CR3` is a guest-written register; `paging::walk` masks it and range-checks
nothing; the entries come back through `Exec::phys_read`, the ordinary address
space, with `MemAttrs::debug` clear. Every `pc-at` and `q35` board maps
`pc.hpet` at `0xfed0_0000` with `AccessConstraints` of `U32` and `U64` —
exactly the widths a legacy and an IA-32e descriptor read use — and the HPET is
lazily advanced, so answering catches it up to this core's live position and
drives `pc.ioapic`'s lines for whatever expired. `pc.lapic` at `0xfee0_0000` is
the same story at `U32`, which a non-PAE walk uses. This board is the one that
maps no MMIO at all, which is why it is the wrong board to have argued from.

So `admit` re-asks `pins_pending` after the translation, gated on `Exec::used`
having changed — true only when a walk actually happened, because a buffer hit
returns before `phys_read` and charges nothing. `Admitted::leave` carries the
answer to both of `admit`'s call sites: `advance`'s prologue and
`Frontend::enter`, which is a chained block's entry translation and was just as
unwatched. The regression test is
`a_walk_that_raises_intr_is_taken_where_the_interpreter_takes_it` — a legacy
page directory mapped over a device, a two-page loop whose `INVLPG`s make both
pages cold on every pass, and a sweep over which walk raises. With the
prologue's check removed `RIP` reads `0x10_1000` where the interpreter reads
`0x10_0010`; with the chained one removed, `0x10_0000` against `0x10_1001`.

It cost, under callgrind over `benches/x86_dispatch --smoke`, with
`Exec::step` as the control row: `X86::run_budget` inclusive
**2 423 634 019 -> 2 423 868 819, +0.0097%**, against an `Exec::step` that
moved by nothing at all — 36 818 446 752 on both sides, to the instruction.
The gate is why: a buffer hit charges nothing, so on a warm block the extra
work is one comparison of two values `admit` already had.

`admit` has one exit this does not cover: a known-unliftable PC on a cold page,
where the walk raises a pin and `Boundary::unlifted` then hands the instruction
to `Exec::step`, whose own first act is to take the interrupt — so the
instruction never runs, where an interpreted core would have run it. Same
reachability, and closing it needs `Exec` to offer one step with the pin check
already discharged, which is a change to the oracle rather than to the engine.

### What is still known to be missing

* **Bytes written by something that is not this core** — a DMA engine, a disk
  controller filling a page cache, another processor, a debugger writing a
  breakpoint — are outside `jit::dispatch`'s contract, which is that a host
  accumulates the pages *it* wrote. The same known gap `cpu::riscv::engine`
  states, from the same cause: closing it needs a write notification from the
  address space for masters that are not the CPU, which `core::space` has not
  got. On this board nothing else writes guest memory while the core runs.
* **A snapshot restore moves a paged guest's clock**, under either engine and
  from before this work: `State::tlb` is derived state and is deliberately not
  serialized (`ROADMAP.md` §4.5), so a restored processor comes back with an
  empty translation buffer and its next accesses pay for walks the machine that
  took the snapshot had already paid for. Those are guest-visible clocks.
  `tests/x86_engines.rs` therefore takes its snapshot comparison in the unpaged
  world, where the buffer is never consulted at all.
* **The rest of the exclusion list**, which is now a long tail rather than a
  headline, and is measured to the opcode: `CMPXCHG` 1 794 000, `SHRD`
  1 523 903, `PUSHF` 1 284 780, `CLI` 1 065 973, `DIV` 955 276, `MOVAPS`
  820 160, `RDTSC` 695 251, `OUT` 470 536, `XORPS` 410 080, the segment and
  control-register `MOV`s 408 644, `BT` 283 549, `IRET` 271 261, `BTR` 232 701,
  `STI` 210 082. **The largest of them is 0.10% of the guest's own
  instructions** and the whole list is 0.66%. Every one is still a decision
  rather than a gap and the argument for each is in `cpu::x86::lift`'s table;
  what has changed is that the *whole list* is now worth two thirds of a

* ~~**The budget guard**, which is 2.02% of the guest on its own.~~ **Gone**,
  and the sections above are what replaced it. What is left of the interpreted
  remainder is the exclusion list plus 0.35 M interrupt shadows and pins, and

## Where the host instructions go

Everything above this heading is *what* the engine runs and how much of the
guest it covers. This section is the other question — **where the host's own
instructions go while it does that** — and it is the first time it has been
asked on this core. `benches/x86_linux_boot` exists to ask it: it boots this
board for a span of guest time and prints the census a profile has to be
divided by, because a host instruction count means nothing without the block
count and the retired count beside it.

It exists as a *second* benchmark rather than as a reading of
`benches/a64_linux_boot` because the two frontends are not interchangeable and
the A64 conclusions could not be assumed to transfer. Both cores spend most of
their host instructions on per-**block** work, so what decides where the next
win is, is how many guest instructions a block covers — and before this round
this core's number was 5.21 against A64's 6.44.

### The method

`scripts/fetch-testdata.sh x86-linux initramfs-x86`, which is a Debian trixie
installer amd64 `bzImage` (12 122 048 bytes) and a busybox initramfs — **the
pair `tests/engine_longrun.rs` boots, and not the Gentoo `6.6.67` image the
wall-clock table above was taken with.** Two different guests: the counters in
this section and the counters in that one are not comparable term by term, and
each is internally consistent.

`engine = "jit-host"`, 256 MiB of extended memory, `nokaslr
cryptomgr.notests`, one rep. The **census** is nine hundred guest seconds —
the same budget `scripts/check.sh long` gives the lockstep gate — run
natively; the **profile** is a hundred and twenty, run under callgrind, and
the subsection after this one is why the two spans differ:

```text
  cargo bench --features machine-pc64,cpu-x86-lift,jit,jit-x86 \
      --bench x86_linux_boot -- --seconds 900

  valgrind --tool=callgrind --smc-check=all-non-file --cache-sim=no \
      target/release/deps/x86_linux_boot-… --seconds 120 --reps 1
```

`--smc-check=all-non-file` is **not optional**: the generated code lives in an
anonymous mapping this process writes and then executes, and valgrind's default
translation cache would run the bytes it saw first. `--cache-sim=no` because
what is wanted is instructions retired rather than a cache model, and `--hash`
is left off because hashing this board walks every byte of its extended memory
and would land in the profile as if it were emulation.

Shares are **self** cost — what a function executed itself, not what it called
— so they add rather than nest. The code the JIT generated has no symbol at
all, because it is an anonymous mapping; it is the sum of callgrind's unnamed
`0x…` entries.

### One thing the method cannot do, said before the numbers

**A nine-hundred-second boot does not finish under callgrind in useful time**,
and it is worth writing down because the obvious reading of the table below is
*"why not run it for the same span as everything else"*. On an idle 64-core
host it starts at about **480 M host instructions per second** while the guest
is in its own decompressor and is under **40 M** once the kernel proper is
running: after sixty-three minutes it had covered 769 G of an estimated 1.09 T
and the rate was still falling. `--smc-check=all-non-file` is why —
it makes valgrind re-check its own translations of the anonymous mapping this
process writes and then executes, and the kernel phase is where the JIT
compiles a hundred thousand distinct blocks into that mapping rather than two
thousand. It is also not optional, so this is a property of profiling a JIT
rather than a knob. **Under load it is far worse**: the first attempt at this
pair ran beside forty other builds and managed 8 M per second in the kernel,
which extrapolates to a day.

So the attribution below is taken over **the first hundred and twenty guest
seconds**, which on this board is entirely the kernel's own self-decompressor:
several hundred million instructions of straight-line integer arithmetic and
memory traffic, paged, all of it inside the lifted subset. It is a real
x86-64 workload and it is the same one the wall-clock table's second column is
about. What it is *not* is the kernel, and "what the kernel phase says" below
is how far that could be checked.

The **census** and the state hash in the next section are over the whole nine
hundred seconds, natively, because those cost fifty-three seconds rather than
a day.

### What was done about it: a store no longer ends a paged block

`cpu::x86::lift::Smc::HostGuard` is that measurement acted on, and it is the
same move `cpu::arm::a64::lift` made a round earlier — recorded in
`cpu::x86::lift`'s module docs at the time as *"it would work here, and nobody
has done it"*.

A store into the page a block was lifted from is now noticed by the **host**,
which sees the guest-physical page of every store the block makes
(`Exec::wrote`, which already feeds `jit::DirtyPages`) and compares it against
the physical page the entry translation resolved to (`Admitted::frame`). A
match retires the run's tick allowance, so the block leaves at its next guest
instruction boundary — which for a store is the one its own instruction ends
at, and which is where `Dispatcher::run` drains the dirty log into the block
cache. The frontend emits nothing for it.

What that replaced is the expensive half of a split. `admit` used to pick
`Smc::EndBlock` whenever the guest paged — because the in-block guard compares
**linear** pages and two of them may alias one physical page, so `lift` refuses
it there — and a paged guest is every guest that matters. A store was therefore
a whole block dispatch, on the hottest instruction class x86 has after the ALU.
The new comparison is physical at both ends, so it has no aliasing hole and it
is the same policy in all four worlds.

constant, the same guest: **1 528 989 622 guest instructions** either way and
the same `Machine::state_hash` of `0xb996f48fb92dd24b`, so the two columns are
the same work.

**The generated code itself shrank by an eighth**, which reads like an error

and there are 3.3× fewer blocks. Nothing about the code inside a block changed.

two is one build: `Smc::HostGuard` with the call merge left disabled gives
127 989 508 blocks and **11.90** guest instructions per block. So the policy is
5.21 → 11.90 and the merge it unlocks is 11.90 → 12.17.

### What it cost, and the one thing it made unsound

Flag elision at exactly one boundary per store. `Flags::Elide` may omit a flag
from a boundary's live map when the instruction that boundary opens
unconditionally writes it and cannot fault — which is a claim about what
nothing can observe *between* two boundaries, and a boundary the block may
**leave** at is one the guest stands on with an interrupt able to push a stale
`EFLAGS`. `Smc::Guard` never had the problem, because it leaves through an exit
sequence whose live map names every flag; `Smc::HostGuard` leaves at an
ordinary boundary. `lift::Lifter::after_store` is the answer — the boundary
opened for a store's successor elides nothing — and
`a_boundary_the_host_guard_leaves_at_names_every_flag` is the regression, which
is the one mutation every other test in
`tests/x86_lift_differential.rs` survived.

This engine ships `Flags::Eager` anyway, for the reason its own `FLAGS`
constant gives, so the cost is paid by the benchmark ladder rather than by the
board.

### And what it did not cost

A store was the boundary for three things and not one. The other two are
answered in `IrHost::store`, where the store happens:

* **an interrupt the store raised** — an APIC `ICR` write, an 8259A command,
  any device that answers by pulling a wire. This core already paid for it,
  because `Smc::Guard` had already made a store an ordinary instruction with
  paging off, and `docs/platforms/pc64.md`'s own "A load from the APIC can
  raise `INTR`" section is where that was found;
* **a store that remapped the address space.** `Frontend::epoch` reads the
  topology generation at every *block* boundary, which was sufficient while a
  store was the last instruction in its block. It is one relaxed atomic load
  per store now. A64 pays the same one and also has to retire the host pointers
  its backend took out of the shadow TLB at block entry; this core now has a
  shadow too, and `paging::Tlb::sync` retires those pointers on the same call
  that flushes this core's own translation buffer.

## The inlined memory path

The row above says an access on this core cost a call where A64's cost a mask,
a compare and an add. This section is that row closed, and it is the largest
single change any profile of this project has produced: **−25.7% of the whole
run**, on the same guest, with the same state hash.

### Why there was no fast path, exactly

`jit::x86`'s `Compiler::inlinable` refuses to inline an access whose `MemOp`
carries a `SegId`, and until this round every access `cpu::x86::lift` emitted
carried one. Both halves of the seam said no, and both were right:

* The **backend's** refusal is that a segmented access is translated before it
  reaches the TLB — `Exec::read_mem` adds the base, checks the limit, the
  access rights and the present bit — and that translation is the frontend's.
* The **frontend** carried the register because the fault differs by it: a
  stack violation is `#SS` where every other segment raises `#GP`, and the
  descriptor is hidden state a `MOV DS, ax` replaces between two instructions.

What was *not* true is the part everyone repeated: that "an x86 load's address
is an effective address" makes it un-inlinable. Base plus index times scale plus
displacement, and the 32-bit wrap, are **already in the IR** — `Lifter::ea`
computes them and `World::addr_mask` wraps them. The only thing missing was the
segment base, and **in long mode there is no segment base**: `CS`, `DS`, `ES`
and `SS` are defined to have a base of zero and no limit whatever their
descriptor caches hold (*Intel SDM* volume 3 §3.4.4), which `World::of` already
writes into `World::seg_base` without consulting a descriptor. The fold this
core was refusing to lower is, in the only world `pc64` spends its time in, the
identity.

So the genuinely hard part was never the arithmetic. It was three smaller things
that the arithmetic was hiding, and each is a refusal in the shipped design:

* **The fault vector.** Clearing `MemOp::seg` clears the one thing
  `Exec::seg_linear` reads out of it in long mode — `#SS(0)` through the stack
  against `#GP(0)` through everything else. The three data segments need
  nothing, because the host answers `#GP(0)` from its own canonical test. The
  stack gets `lift::STACK`: `(addr + 2^47) < 2^48` unsigned, branched over in
  the case that always holds. Refusing `SS` instead would have given up every
  `PUSH`, every `POP` and every `[RSP+n]` operand a compiler emits.
* **`FS` and `GS` are refused outright.** Their bases come from an MSR and are
  live state, and under `Origin::Paged` a block is keyed by the physical page of
  its bytes and **not** by `World::generation` — so a block that folded a `GS`
  base in would be reused under a different one. Linux puts its per-CPU area
  behind `GS`, so this is a real exclusion and not a hypothetical one.
* **The open bus, which is where the `jit` seam runs out.** `State::open_bus` is
  in the snapshot and therefore in `Machine::state_hash`, and `Exec::phys_read`
  latches it on every bus cycle. An access the **backend** serves never reaches
  `IrHost::load`, and `FastMem::note_fast_load` is handed neither the address
  nor the value, so there is nowhere for the byte to come from. The block
  carries it instead, in the `lift::OPEN_BUS` slot — one shift per inlined
  access — and that is why an instruction that can fault **after** its access
  keeps the call: a slot is published at a boundary, and a fault publishes the
  boundary the instruction *started* at, which is one bus transaction stale.
  `lift::Plan::one_last_access` is the list, written default-deny, and what it
  excludes is every read-modify-write (`add [m], r` on a copy-on-write page is
  the case that would have diverged), `RET`, `JMP r/m`, `CALL r/m`, `PUSH [m]`
  and `POP [m]`.

### What it does, and what it refuses

The table generated code probes is a `jit::Tlb` shadow hung off
`paging::Tlb` — the same arrangement `cpu::riscv::mmu` and `cpu::arm::a64::mmu`
use, and in the same place, so that every eviction this core's own data buffer
makes is an eviction of the shadow at the same index. Two differences from
those cores are x86's own:

* **One data array serves loads and stores**, so a load's walk can evict the
  entry a store was using; `Tlb::insert` therefore clears the shadow slot in
  *both* sets and the fill that follows rewrites only the one the walk was for.
* **Only a part with `Buffers::Split` gets a shadow at all.** A 386 and a 486
  put data translations in the thirty-two-slot instruction array, which a
  sixty-four-slot shadow cannot index in lockstep with. `lift` already refuses
  paged code on those parts.

Refused, in full: everything below long mode, `FS` and `GS`, paging off, the
A20 gate shut, a unified translation buffer, and every instruction that touches
memory twice or can fault after its access. On a nine-hundred-second `pc64`
boot that leaves **0.187 inlined loads and 0.107 inlined stores per guest
instruction** — 447 M accesses the backend served itself.

### What it did not break, and how that was checked

* **`MemResult`'s three-way distinction.** The inlined path cannot fault: it is
  taken only after the probe finds a tag match and a host address, and every
  other outcome branches to the call, which is `Exec`'s own path unchanged.
* **`MemAttrs::debug`.** A debug read never runs generated code, and
  `jit::Tlb::fill` caches only a page that resolves to a direct `RamStore` — so
  there is no device the fast path can reach and no FIFO it can pop.
* **`Perms::EXEC` on fetches.** The shadow's fetch set is never filled:
  `Exec::refresh_shadow` returns at once for `access.fetch`, because a block
  makes no fetches and an entry nothing reads is an entry that can only be
  wrong.
* **The exclusive monitor.** `SpaceView::write` breaks a reservation on every
  store that goes through the address space and nothing at all breaks one on a
  store that does not, so `note_fast_store` calls `monitor().note_store` itself.
  `an_inlined_store_breaks_the_reservations_an_interpreted_one_breaks` reserves
  every kibibyte of guest RAM on two machines, runs the same program through
  both engines, and compares the survivors.
* **The dirty bitmap.** `jit::Tlb::note_fast_store` marks it, and
  `an_inlined_store_leaves_the_dirty_pages_an_interpreted_one_leaves` compares
  the two engines' dirty sets page for page.
* **The A20 mask.** `Exec::masked` folds bit 20 out of a physical address and
  the shadow's host pointer was resolved before that fold, so a shut gate makes
  the two different pages. `Exec::refresh_shadow` fills nothing and
  `Exec::mem_plan` publishes nothing while the gate is shut — which is belt and
  braces, since `World::of` already refuses to lift at all there.
* **`Smc::HostGuard`.** An inlined store reports its guest-physical page through
  `Exec::note_write` and then runs `Host::note_writes`, which is the same
  comparison against `Admitted::frame` an interpreted store makes.
  `a_long_mode_store_into_a_running_blocks_own_page_is_honoured` is the gate and
  it now exercises the inlined path.

### What the kernel phase says, as far as it could be seen

Two nine-hundred-second pairs were run as far as they would go — to about
773 G and 586 G host instructions, which is well into the kernel — and made to
dump what they had. The two sides are at **different** guest points, so their
absolute counts are not comparable; their *shares* are, and they say the
decompressor's table holds where the boot goes next:

| | ends the block | the host guard |
| --- | --- | --- |
| the address space | 22.90% | 28.69% |
| the dispatch loop (`X86::run_budget`) | 14.50% | 7.33% |
| replaying deferred bookkeeping (`flush_thunk`) | 10.80% | **12.32%** |
| the entry fetch translation | 10.23% | 10.48% |
| admitting a block (`admit` and `world_of`) | 9.10% | 4.41% |
| the code the JIT generated | 7.88% | 8.62% |

Every share falls where the work is per block and rises where it is per
access or per event, which is what a shorter block does to a profile and not
what anything else does. A second pair taken on a loaded host at a different
point agrees to within a few tenths of a point on every row.

That last pair is the one to carry forward, and it is A64's finding restated
on this core: **what is left to aim at has moved.** The replay of deferred
charges and boundaries is now the largest row in the profile after the address
space, and what shortens it is fewer *events* rather than fewer blocks.

## KVM, and what a snapshot means when the engine can change

`machines/pc64.machine` declares `engine` as a `param`, so this board is one of
the places where all three engines are reachable from the command line — and
`AccelCpus::install` makes a fourth, replacing `cpu.x86`'s binding so the same
machine file runs its processor on host silicon. `ROADMAP.md` phase 7 gates that
on a property the other three get for free: **a snapshot taken under one engine
has to restore under another.**

Three of the four are the same device. `engine = "interp"`, `"jit"` and
`"jit-host"` are execution strategies inside one `X86`, sharing one `State` and
one chunk, so a snapshot crossing between them is not crossing anything —
`tests/x86_engines.rs` asserts a bit-identical `Machine::state_hash` across the
switch, which is the strongest statement available. The vCPU is not: it holds
the guest in `struct kvm_regs`, `struct kvm_sregs` and a list of model-specific
registers, and something has to translate.

`src/accel/state.rs` is that translation and
[`docs/system/cpu-state-model.md`](../system/cpu-state-model.md) is the design.
Two things about it are worth knowing before reading this board's numbers.

**The chunk is unchanged, and the bug was in the bridge.** The state model's
first version carried five model-specific registers. This board's core has
thirty-four of them in its chunk — the `SYSCALL` set, `IA32_MISC_ENABLE` and the
nineteen memory-type range registers the section above explains — and the
twenty-nine that were not on the list were written to every snapshot faithfully
and were faithfully zero, because nothing read them out of the vCPU. Zero in
`IA32_MTRR_DEF_TYPE` is not "the default": SDM volume 3A §12.11.2.1 makes `E=0`
mean *every physical address uncacheable*. So an accelerated snapshot of this
board described a machine whose memory types the guest had never asked for.
Fixing that changed no chunk bytes, so `cpu.x86` stays at version 8 and no
existing save state is orphaned.

**`RDTSC` is continuous across the switch; its rate is not.** The counter's
*value* is architectural and crosses in both directions — the model stores what
a `RDTSC` in the guest would return, never a hypervisor's TSC offset, which is
derived from the host's own counter and is meaningless anywhere else. The
*rate* is a property of the machine: an accelerated guest's counter advances at
`KVM_GET_TSC_KHZ` and this core's advances at four ticks per bus cycle plus the
manual's execution figures. A kernel that has calibrated its TSC against the
PIT or the HPET and is then restored under the other engine will recalibrate or
mark the clocksource unstable. That is not a snapshot field anyone can add; it
is a board that would have to pin the two rates together, and this one does not.

`tests/x86_arch_state.rs` is the gate, on a smaller board than this one for
`tests/x86_engines.rs`'s reason — this board wants a `bzImage` and that test
must stay hermetic. It runs all four crossings that involve hardware
(KVM↔interpreter, KVM↔JIT) and makes the **guest** the witness: the program
reads its own registers back with `RDMSR` after the restore, so what is asserted
is what the destination engine actually gave it rather than what two copies of
this crate agree about.
