# `pc64` — a PC with a long-mode processor and no firmware at all

Consumed by: [`machines/pc64.machine`](../../machines/pc64.machine) and
[`src/dev/linuxboot.rs`](../../src/dev/linuxboot.rs). The chips are the ones
[`pc-at.md`](pc-at.md) documents; nothing here re-describes them.

`pc-at` and [`q35`](q35.md) are boards for **firmware**: they have a ROM socket,
a video adapter and a disk, and what runs on them starts at `0xfffffff0` in real
mode. This is a board for a **kernel**. There is no firmware on it: the object
at the bottom of the machine file writes a `bzImage` into memory and enters it
at its own 32-bit entry point, which is the one interface a Linux kernel offers
to something that is not a BIOS.

That makes it the smallest machine that can answer `ROADMAP.md` phase 6b's real
question — *does the x86 core survive a modern kernel's early boot* — without
also being a test of a boot loader, a partition table and an option ROM.

## The device set

Eight objects, and each earns its place by something the kernel does.

| Object | Why it is there |
| --- | --- |
| `cpu.x86`, `variant = "x86-64"` | the point of the board |
| two `pc.pic` | somewhere for IRQ0 to land; the board stays in PIC mode |
| `pc.pit` | the tick, and `quick_pit_calibrate` |
| `pc.sysctl` | port 0x61, which that calibration gates counter 2 through |
| `pc.rtc` | the wall clock, read out of CMOS |
| `uart.ns16550` | the console — `console=ttyS0` is how a machine with no video adapter says anything |
| `x86.linuxboot` | the kernel, the zero page, the e820 map and the stub that enters them |

No APIC: with no ACPI tables and no MP table there is nothing to tell the kernel
how interrupts are routed, so it stays in PIC mode — and `CPUID`'s APIC bit
follows the *board* rather than the part (it is set only when a local controller
is wired to the core), so the two agree. No 8042, no video, no DMA controller,
no IDE, no PCI: each would be a second thing being tested.

## How a kernel is entered

[`src/dev/linuxboot.rs`](../../src/dev/linuxboot.rs) implements the Linux/x86
boot protocol's loader side. It is an ABI between a boot loader and an image
rather than an implementation, and every field was read out of a real `bzImage`
and cross-checked against `file(1)`'s independent parse of the same bytes — the
image is *data* being loaded, which is the black-box use `ROADMAP.md` §1 allows.
No kernel source was consulted.

```text
  0x00001000  the stub: real mode in, protected mode out, and its GDT
  0x00007000  boot_params — "the zero page", built from the image's own header
  0x00008000  the kernel command line
  0x00100000  the protected-mode kernel, at its own code32_start
  high        the initial ramdisk, as high as the header allows
  0xfffffff0  the `reset` region: jmp far 0000:1000
```

**The processor is not set up from outside.** A device may not reach into a core
and set `CR0`, and it does not have to: the state the 32-bit entry point asks
for is eleven instructions away, and executing them tests the core rather than
bypassing it. The same choice `riscv.boot` makes, for the same reason.

A 64-bit kernel entered this way brings itself the rest of the way — its
decompressor builds identity page tables, sets `CR4.PAE` and `EFER.LME`, enters
long mode, decompresses several megabytes and jumps to the 64-bit kernel — all
before it has printed a single character. Anything that reaches the first line
of output has already exercised most of what 6b added to the core.

### `nokaslr` is on the default command line, and it is not a preference

Address-space randomisation draws entropy partly from the 8254: it issues a
read-back command and spins until the **null-count** bit in the status byte goes
clear. That bit is set by a control-word write and cleared when a count is
actually loaded (Intel 8254 data sheet, "Read-Back Command"), so on a machine
where nothing has ever programmed counter 0 it never clears — and there is no
firmware on this board to have programmed it. A kernel that randomises therefore
spins in the decompressor forever, before printing anything.

Both halves of that are correct behaviour. The combination is what a board with
no BIOS produces, and it is the kind of thing only a real guest finds.

## What it was measured doing

[`tests/pc64_linux.rs`](../../tests/pc64_linux.rs) is gated on `RSEMU_KERNEL`,
so `cargo test` stays hermetic and offline; point it at a `bzImage` and it runs
one. Every line below is a byte the guest itself wrote to its own serial port,
running a stock distribution kernel — 12.7 MB, `6.6.67`, `SMP PREEMPT_DYNAMIC`
— that this project has never built, patched or read:

```text
[    0.000000] Linux version 6.6.67-gentoo-x86_64 … #1 SMP PREEMPT_DYNAMIC
[    0.000000] Command line: console=ttyS0,115200 earlyprintk=ttyS0,115200 nokaslr
[    0.000000] BIOS-provided physical RAM map:
[    0.000000] BIOS-e820: [mem 0x0000000000000000-0x000000000009ffff] usable
[    0.000000] BIOS-e820: [mem 0x00000000000a0000-0x00000000000fffff] reserved
[    0.000000] BIOS-e820: [mem 0x0000000000100000-0x00000000100fffff] usable
[    0.000000] printk: bootconsole [earlyser0] enabled
[    0.000000] NX (Execute Disable) protection: active
[    0.000000] No local APIC present
[    0.000000] APIC: disable apic facility
[    0.000000] smpboot: Allowing 1 CPUs, 0 hotplug CPUs
[    0.000000] printk: console [ttyS0] enabled
[    0.003333] APIC: Keep in PIC mode(8259)
[    0.026666] tsc: Using PIT calibration value
[    0.033333] tsc: Detected 25.823 MHz processor
[    0.019012] Calibrating delay loop (skipped) … 51.79 BogoMIPS (lpj=86076)
[    0.126139] x86/fpu: x87 FPU will use FXSAVE
```

Four of those lines are claims about *this* work and each is the board
answering rather than a constant: the e820 map is the one the loader built from
the machine file's own `basemem` and `extmem`; `NX … active` means `CPUID`
leaf `8000_0001`, `EFER.NXE` and bit 63 of a page-table entry all agree;
`No local APIC present` is `CPUID`'s APIC bit following the *board*; and
`Detected 25.823 MHz processor` is the kernel measuring this core's time-stamp
counter against this board's 8254 and getting a stable number.

One thing worth noticing further down the log: `watchdog: BUG: soft lockup` is
not a defect. The guest measures its own time against a counter that runs at
guest speed and compares it with one that does not, and the trace under it
shows a timer interrupt arriving through the 8259A and the 8254 in 64-bit
mode — which is the interrupt path working rather than failing.

## Userspace, and the two things that were in the way

The board now reaches a **shell prompt that echoes what is typed at it**:

```text
[  488.441711] Run /init as init process

rsemu initramfs on Linux 6.6.67-gentoo-x86_64 x86_64
/bin/sh: can't access tty; job control turned off
rsemu# ^[[6nuname -srm
Linux 6.6.67-gentoo-x86_64 x86_64
```

The last two lines are the only ones on this page that came back *in* rather
than out: `uname -srm` was fed to the 16550's receiver by the test's
`RSEMU_KERNEL_INPUT` script, and the guest echoed it and answered it. Nothing
before that had exercised the receive half of the UART at all. The `^[[6n`
between the prompt and the echo is the shell asking the terminal where the
cursor is; it is left in rather than tidied away, because everything on this
page is what the guest actually wrote.

Getting there needed two things, and neither was a defect in the board.

**A root.** There is no disk here and there is no PCI, so an initramfs is not
the cheap option, it is the only one: `nvme`, `ahci` and `virtio.blk` are all
PCI devices with no host bridge to sit behind, `pc.ide` would decode at
`0x1f0` happily enough — and the guest would never look, because a
distribution kernel builds `libata` and `virtio_mmio` as *modules* and the
modules live on the root that is not mounted yet. The kernel's own log settles
it: `PCI: System does not support PCI`, `SCSI subsystem initialized`, and no
storage driver of any kind registering. `scripts/fetch-testdata.sh
initramfs-x86` therefore builds one, around busybox, exactly as the
`initramfs` target does for `riscv-virt`.

**Time.** The kernel's crypto self-tests are hundreds of guest-seconds of
arithmetic between `Loading compiled-in X.509 certificates` and
`Freeing unused kernel image`, and they are what a nine-hundred-second run was
spending itself on. `cryptomgr.notests` on the command line removes them
outright. It is a *guest* choice rather than a board one, so it stays out of
`machines/pc64.machine`'s default `cmdline` — the board describes hardware —
and lives in the command below instead.

```text
scripts/fetch-testdata.sh initramfs-x86

RSEMU_KERNEL=/boot/vmlinuz \
RSEMU_INITRD=testdata/x86/initramfs-x86.cpio \
RSEMU_KERNEL_CMDLINE='console=ttyS0,115200 nokaslr cryptomgr.notests' \
RSEMU_KERNEL_MS=1200000 \
RSEMU_KERNEL_INPUT='rsemu# =>uname -srm\n' \
RSEMU_KERNEL_STOP_AT=x86_64 \
    cargo test --release --features machine-pc64 --test pc64_linux -- --nocapture
```

### What it costs

Measured on one host, release build, interpreter, and the ratio is the part
that travels:

| Run | Virtual | Wall | Where it ended |
| --- | --- | --- | --- |
| board default, no initramfs | 900 s | 236 s | inside the crypto self-tests, still making progress |
| initramfs + `cryptomgr.notests` | 931 s | 254 s | a shell prompt, `uname` answered |
| the same, built with `jit-x86` | 931 s | 255 s | the same, byte for byte |

**Virtual time runs about 3.7× faster than wall-clock time here, not 1:1.**
Roughly 250 virtual seconds of that is the decompressor, which is solid
computation and closer to 2.8×; the rest of the boot spends much of itself
halted between timer interrupts, and the scheduler does not pay wall-clock time
for virtual time nothing is running in. This page previously implied about
1:1, which is worth correcting rather than repeating: the number depends on
the host, on how much of the boot is idle, and on how much of it is
decompression, so it is a thing to measure per run and not a constant.

## What this found in the core

Six, and the first four each produced a guest that stopped dead with **nothing
printed at all** — which is what makes a board like this worth having. A unit
test cannot ask the question "does the whole of early boot work"; only early
boot can. The fifth needed userspace to find, and said so out loud. All six are
closed, as is the MTRR finding below them.

1. **`IA32_MISC_ENABLE` (`0x1a0`) raised `#GP`.** The decompressor's processor
   check clears the execute-disable lock through it *before there is an
   interrupt descriptor table*, so the fault was a triple fault forty
   instructions in.
2. **A null selector loaded into `SS` raised `#GP` in 64-bit mode.** It is legal
   there below ring 3 (*Intel SDM* volume 3 §5.4.1), and the first thing a
   64-bit kernel does after its long jump is load all six segment registers with
   zero.
3. **`MOV r64, CR2` transferred thirty-two bits.** In 64-bit mode the operand
   size is 64 bits with no `REX.W` and a `66` prefix cannot narrow it. The
   kernel's early page-fault handler reads `CR2`, subtracts `PAGE_OFFSET`, and
   decides the address is out of range when the top half is missing; it then
   declines to map the page, falls through to a handler with no fixup, and halts
   in a loop with no console.
4. **`POP` to memory addressed its destination before the increment.** *Intel
   SDM* volume 2, `POP`: the effective address is computed *after* `RSP` moves.
   `pushf` / `pop 0x10(%rsp)` is how a compiler writes `local_irq_save` on
   x86-64, so the flags landed eight bytes low, on top of a live local. The
   kernel lost a function argument that way in `text_poke` — the routine that
   rewrites its own code — and died with a null-pointer dereference sixteen
   instructions later, thirty-two seconds in.
5. **The packed-integer half of SSE2 is not decoded, and `CPUID` says it is.**
   This one is the first thing *userspace* found, and it found it immediately:

   ```text
   [  490.348390] Run /init as init process
   [  490.575039] traps: init[1] trap invalid opcode ip:4a80b6 sp:7fff8accf530 error:0 in busybox[401000+18c000]
   [  490.597064] Kernel panic - not syncing: Attempted to kill init! exitcode=0x00000004
   ```

   The bytes at that address, from the kernel's own `Code:` line, are
   `66 0f 6e ca` — `MOVD xmm1, edx`, which the core has — followed by
   `66 0f 62 c8`, which is `PUNPCKLDQ xmm1, xmm0` (*Intel SDM* volume 2,
   `PUNPCKLBW/PUNPCKLWD/PUNPCKLDQ/PUNPCKLQDQ`), which it does not. That is
   glibc's static startup packing two `CPUID` results into one XMM register,
   about a hundred instructions into the first user-mode program on the
   machine.

   `src/cpu/x86/isa.rs`'s `SECONDARY_66` table carried the packed-*double*
   half of SSE2 in full and, of the packed-integer half, only `MOVD`, `MOVDQA`,
   `MOVQ`, `PAND`, `PANDN`, `POR` and `PXOR`. Everything from `66 0F 60` to
   `66 0F 76` — the unpacks, the packs, `PSHUFD`, the shift group and the
   compares — and the whole `66 0F D4`-`66 0F FE` arithmetic block were absent,
   while `CPUID.01H:EDX[26]` is set for `variant = "x86-64"`. A guest that
   believes `CPUID` is entitled to all of them.

   **Closed.** The sixty-two encodings are in the table, in the three shift
   groups Intel numbers 12, 13 and 14, and in the `F3`/`F2` maps for the two
   half-register word shuffles — gated on `Features::sse2` rather than turned
   on unconditionally, so a part configured without the bit still raises `#UD`
   for every one of them and `CPUID` and the decoder keep saying the same
   thing. The interpreter executes them in `fpexec::sse_packed`; there is no
   MMX form of any of them, because there are no MMX registers here.

   The fixture still fetches busybox.net's statically linked **musl** build,
   because that is what the script downloads; the glibc path is what this
   finding was about and the encodings it stopped on now decode, but a
   glibc-linked userspace has not been run end to end on this board since.
6. The reserved-NOP space (`0F 18`-`0F 1F`) was missing, which is `#UD` on the
   first `ENDBR64` of a kernel built with indirect-branch tracking.

### And one that is the board rather than the core

With `CONFIG_DEBUG_VM_PGTABLE` on, the kernel warns twice during `init`:

```text
pmd_set_huge: Cannot satisfy [mem 0x00200000-0x00400000] with a huge-page mapping due to MTRR override.
WARNING: CPU: 0 PID: 1 at mm/debug_vm_pgtable.c:441 debug_vm_pgtable+0x1b50/0x1de0
```

The line above both of them was `MTRRs disabled (not available)`: the core did
not advertise `CPUID.01H:EDX.MTRR[12]` and answered `RDMSR 0xfe` with `#GP`, so
the kernel declined to install a 2 MiB mapping it could not prove was
write-back, and its own page-table self-test then warned that `pmd_set_huge`
returned zero. The boot continued and nothing else noticed.

It was a gap in the *preset* rather than in this board, and it is closed. Every
part that implements long mode also implements the memory-type range registers,
so `Features::mtrr` is part of `Features::X86_64` and `Features::validate`
now refuses a long-mode part without it. The core has `IA32_MTRRCAP`,
`IA32_MTRR_DEF_TYPE`, the eight variable base/mask pairs and all eleven fixed
ranges, with the reserved bits and the two undefined memory types refused
exactly as hardware refuses them — which is what lets a guest probe.

They are **stored and reported, not obeyed**, and `prot::mtrr` argues why that
is the whole truth rather than a shortcut: a memory type says what a cache may
do, this core has no cache, every access is one bus transaction in program
order, and that behaviour satisfies `UC` — which is a legal implementation of
every weaker type. No guest can construct an experiment that separates this
answer from a processor with its caches disabled. Add a cache model and the
registers stop being storage.

## The JIT, and why `engine = "jit"` is not a line you can write yet

`jit-x86` is a real host code generator and `tests/x86_lift_differential.rs`
runs compiled blocks against the interpreter on generated corpora. **None of
that is reachable from a machine**, and a boot on this board is the clearest
possible demonstration: building the same test with `--features jit-x86` and
without it produces console output, register state, `CR2`/`CR3`, the stack dump
and the virtual-time total that are **byte-for-byte identical** — 849 lines of
guest output, through the shell prompt and the command typed at it, with no
diff — for 931 529 virtual milliseconds in both, at 254.2 s of wall clock
against 254.6 s. The feature is inert here, and the run is reproducible, which
is the determinism half of the claim.

Two separate things stand between this board and compiled execution, and only
the first is wiring:

1. **No CPU core has a JIT execution path.** `X86`'s `Runnable::run` calls
   `run_budget`, which calls the interpreter's `step` in a loop;
   `jit::Dispatcher` appears only in `cpu::x86::differential` and
   `cpu::riscv::differential`, driven by their own synthetic frontends and
   hosts. Every core's `engine` property accepts exactly one value, `"interp"`.
   Wiring it means a `Dispatcher` per core, its `Tlb` fed from the core's own
   address space, `Frontend` and `IrHost` implementations over the core's real
   state rather than the harness's, and the safe-point protocol carried through
   the dispatcher's exit flag.
2. **The x86 frontend refuses this guest outright.** `lift::World::of` returns
   `None` — no block, nothing compiled — for a core in long mode
   (`if sys.sixty_four()`) and for a core with paging on (`if sys.paging()`),
   and `src/cpu/x86/lift.rs` states both as decisions rather than omissions:
   long mode is "a second operand-size and address-size lattice", and paging
   would make an instruction fetch's tick charge depend on whether the guest's
   own TLB is warm. A 64-bit kernel is in long mode with paging on from the
   decompressor onward, so **every** block on this board is untranslatable
   today. Wiring the dispatcher in would produce a boot that is bit-identical
   and no faster, which is exactly what the measurement above already shows.

The consequence for anyone hoping a Linux kernel is a big differential corpus:
it is, but not for x86 yet. `pc-at` and `q35` run 32-bit protected-mode
firmware with paging off, and that is the guest inside the current subset.
