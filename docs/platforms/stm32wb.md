# STM32WB55 / STM32WB35 — the `stm32wb55` and `stm32wb35` machines

Consumed by: `machines/stm32wb55.machine`, `machines/stm32wb35.machine`,
`scripts/gen-stm32wb-machines.py`, `src/dev/stm32/`, `src/cpu/arm/v7m`.

Two real parts, one reference manual. The **STM32WB55RGV6** is the
microcontroller on ST's NUCLEO-WB55RG (the P-NUCLEO-WB55 pack): a Cortex-M4F
at up to 64 MHz, 1 MiB of flash, 192 KiB of SRAM1 and 64 KiB of SRAM2, and a
Cortex-M0+ that runs the radio. The **STM32WB35CEU6A** is the same family with
512 KiB of flash, 32 KiB of SRAM1, and no GPIOD, LCD, SPI2 or TSC.

```sh
rsemu run stm32wb55 --media firmware=app.bin
rsemu run stm32wb35 --media firmware=app.bin
```

The firmware image is loaded at `0x08000000` (and seen at zero through
SYSCFG's boot alias, as on an F4), and USART1 — the Nucleo's ST-LINK virtual
COM port, PB6/PB7 — is the terminal.

The two machine files are generated by `scripts/gen-stm32wb-machines.py`.
Edit the script and rerun it; do not edit the files by hand.
[`stm32wb-inventory.md`](stm32wb-inventory.md) is the table the script is
drawn from — every base, size, vector and RCC bit, and the exact WB35 diff.

## BLE, and what "no radio" means

CPU2 is **not an executing core** here. On the silicon it runs ST's
encrypted wireless stack, which cannot be run; `cpu2` is `st.wb-cpu2`
([`../devices/stm32wb-cpu2.md`](../devices/stm32wb-cpu2.md)), a bus master
that behaves like that stack:

1. Firmware lays out the mailbox reference table at the start of SRAM2a and
   sets `PWR_CR4.C2BOOT` (`HAL_PWREx_ReleaseCore`). `pwr.c2boot -> cpu2.boot`.
2. CPU2 reads the table, fills the device information table, and posts the
   system READY event on the system queue, ringing IPCC channel 2.
   `ipcc.c1-rx -> cpu.irq44` takes it to the NVIC.
3. `SHCI_C2_BLE_Init` and the rest of the system commands are answered in
   place in the system command buffer; BLE HCI and ACI commands on channel 1
   are answered with Command Complete or Command Status events, as AN5270
   says each one is. GAP and GATT state is real: handles are allocated as the
   stack allocates them, characteristic values are kept, advertising
   parameters and data are recorded.
4. Event buffers come from the pool CPU1 provides and go back on channel 4.

**Nothing is ever on the air.** Advertising is accepted and goes nowhere, no
peer ever connects, a scan reports nothing and a GATT client procedure never
completes. Firmware that only needs its BLE init to succeed — the usual
reason to run a WB image in an emulator — gets through it; firmware that
waits for a connection waits forever, as it would in a room with no phone.

The flash's **secure area** is where ST's stack would sit, and it is
modelled: `FLASH_SFR.SFSA` defaults to where the full BLE stack v1.25
installs (page `0xD0` on 1 MiB, `0x5C` on 512 KiB), and CPU1 reads zero there
and cannot program or erase it.

| Flash, 4 KiB pages | `st.flash`, `variant = "wb"` | double-word programming, `CFGBSY`/`PESD`, the secure area behind `SFR` |

| RCC | `st.rcc`, `variant = "wb"` | MSI 4 MHz out of reset; HSE32 with `HSEPRE`; the WB `HPRE` table; `HPREF`/`C2HPREF`/`SHDHPREF` handshakes; HCLK2 and HCLK4 drive their own domains; CPU2's gate banks OR onto CPU1's |
| PWR | `st.pwr`, `variant = "wb"` | `C2BOOT`, `VOSF`, the SMPS flags, `DBP` |
| EXTI | `st.exti`, `variant = "wb"` | 49 lines, a mask bank per CPU; direct lines have no EXTI interrupt |

| TIM1, TIM2 (32-bit), TIM16, TIM17 | `st.tim` | TIM16/17 share TIM1's vectors 25/26 |

## Proof

- `tests/stm32wb_board.rs` — always runs: the host plays CPU1's half of the
  mailbox over the board's bus — `C2BOOT`, READY on channel 2,
  `SHCI_C2_BLE_Init`, `HCI_Reset` — plus USART1 receiving into a circular
  DMA ring through DMAMUX1, the IPCC clock gate, the secure flash, and the
  WB35's smaller map.
- `tests/stm32wb_ble.rs` — **ST's own HAL** plus a mailbox client of ours,
  built by `scripts/fetch-testdata.sh stm32wb-ble` from pinned commits with
  `arm-none-eabi-gcc` and the app in `tests/fixtures/stm32wb-ble/`. It runs
  `HAL_Init`, HSE32 → PLL → 64 MHz with HCLK2 at 32 MHz, the LSE, the RF
  wake-up and SMPS clock selection, `HAL_Delay`, an HSEM lock and release,
  then boots CPU2 and drives it: READY, `BLE_Init`, `HCI_Reset`, the version,
  the public address written and read back, `ACI_GATT_INIT`, `ACI_GAP_INIT`,
  the device name, a Battery service and characteristic, discoverable mode,
  `LE_Rand`, an unknown opcode, and a flash page erase and double-word
  program bracketed by `SHCI_C2_FLASH_EraseActivity` — with both IPCC
  interrupts taken through the NVIC. Run it with
  `RSEMU_STM32WB_BLE_DIR=testdata/stm32wb-ble cargo test --release --test stm32wb_ble`.

## What is not modelled, stated plainly

- **The radio**, above, and everything only it would cause.
- **Thread, Zigbee and 802.15.4**: the mailbox tables exist, CPU2 does not
  serve them.
- **ADC1, AES1, AES2, PKA, QUADSPI, SAI1, LPTIM1/2, CRS, COMP, TSC, LCD** have
  no class in the tree; an access to any of these addresses is a BusFault.
  I2C1/3, SPI1/2 and the USB device are placed with **nothing on their
  buses**: no host plugs into `usb` unless something opens it.
- **`USB_HP`** (NVIC 19): `st.usbfs` has one request line and it is wired
  to `USB_LP`; a driver that services double-buffered or isochronous
  endpoints from the high-priority vector will not see them there.
- **DMA requests from anything but the U(S)ARTs and I2Cs.** DMAMUX1's
  request inputs 10–17 are wired; the timers, SPI, SAI, ADC, QUADSPI and AES
  requests are not, so a channel pointed at one of them never moves.
- **Programming the OTP area.** It reads blank; `FLASH_CR.PG` writes to it
  are not modelled.
- **CPU2's view of the shared peripherals**: its own interrupt vectors,
  `SYSCFG_C2IMRx` and `DBGMCU`'s CPU2 freeze bits are storage.
- **The secure SRAM2 pages** (`SRRVR.SBRSA`/`SNBRSA`) are not enforced, and
  their default page numbers come from a forum report rather than a manual.
- **Low-power modes** (Stop 0–2, Standby, Shutdown) and the CPU2 wake-up
  events are register storage only.
- The system bootloader at `0x1FFF0000` is not present.
