# `q35` — the chipset a modern operating system expects, and what it does not have yet

Consumed by: [`machines/q35.machine`](../../machines/q35.machine) and
[`src/dev/q35`](../../src/dev/q35). The source *register* for the platform is
[`ibm-pc.md`](ibm-pc.md); [`pc-at.md`](pc-at.md) is the older board's page and
almost everything on it still applies, because almost every chip is the same
one.

`ROADMAP.md` phase 6b's gate is *a modern Linux distribution booting to a
desktop*. **This board is not that gate**, but the distance has shortened and
this page used to overstate it. The board asked for an `80486` until the core
grew long mode; it now asks for `x86-64`, and a guest booted off its own IDE
drive reaches 64-bit code and prints from there
(`a_guest_reaches_long_mode_and_prints_through_com1_on_this_board`). What is
still missing against 6b is **SMP** — one processor, one local APIC, a MADT
that says so — and a distribution's worth of drivers. Long mode, SSE, x87 and
the four-level walk are in the core and reachable from this board's reset
vector.

## What is actually different from `pc-at`

Four things. Everything else in `machines/q35.machine` is the same object at the
same address as in `machines/pc-at.machine`: two 8259As, an 8254, an MC146818,
an 8042, two 8237As, a local APIC, an I/O APIC, an HPET, a VGA adapter and two
IDE channels. An ICH9 has all of them, so re-describing them would be describing
the same silicon twice.

| | `pc-at` | `q35` |
| --- | --- | --- |
| host bridge | Intel 82441FX, `8086:1237` | Intel 3 Series (G)MCH, `8086:29c0` |
| south bridge | *none* | Intel ICH9 LPC at `00:1f.0` |
| configuration space | `0xcf8`/`0xcfc`, 256 bytes | that **and** ECAM, 4 KiB per function |
| PAM registers | `0x59`-`0x5f` | `0x90`-`0x96` |
| PCI interrupt routing | *none* | `PIRQ[A-H]`, eight routers |
| ACPI | *none* | `PM1_*` at `PMBASE`, and eight generated tables |
| serial port | *none* | a 16550 at `0x3f8` on IRQ4 |
| processor | 80486 | `x86-64` |

The last two are newer than the rest and are the reason the first paragraph
changed. The serial port is a `uart.ns16550` — the chip `riscv-virt` and
`pc64` also use, which is why it lives in `dev/uart/` rather than under any
board. On real silicon COM1 is not in the ICH9 either: it is a Super I/O part
on the LPC bus that the south bridge decodes for (ICH9 §13.1.3, §13.1.4). The
board models the chip and not the decode, because the register file a guest
touches is the 16550's either way.

It earns its place by being the one instrument that works before a video mode
is set and after one is torn down, and by being what `console=ttyS0` names.
The measurement is immediate: the same third-party firmware below reported
`Found 0 serial ports` before it existed and `Found 1 serial ports` after, and
the equipment word at `0040:0010` went from `0x0006` to `0x0206` — bits 11-9
are the count.

### ECAM, and how much PCI Express it is

One mechanism, and one sentence of arithmetic. The Intel 3 Series datasheet
(316966-002) §5.1.16 states it inside `PCIEXBAR`'s own description:

> PCI Express Base Address + Bus Number \* 1 MB + Device Number \* 32 KB +
> Function Number \* 4 KB

That is the whole of [`src/dev/q35/ecam.rs`](../../src/dev/q35/ecam.rs), and it
is enough to enumerate the board. What is **not** implemented, and what each
would cost:

* **Root ports.** A real q35 puts its slots behind ICH9 root ports, which are
  Type 1 configuration headers that forward cycles to a secondary bus.
  `src/bus/pci` has no Type 1 header and nothing that forwards. Everything here
  is on bus 0, which is a legal PCI Express topology — a root complex's
  integrated endpoints live there — and is what an enumeration finds. Anything
  that genuinely needs a bridge (hot-plug, a second segment) needs the Type 1
  header first, and that belongs in `bus::pci`.
* **Express capability structures.** A function with none is a *conventional*
  PCI function as far as software is concerned, which is what every device in
  this tree currently is. Adding one is per-device work, not chipset work.
* **Link state, AER, MSI/MSI-X.** None of them is on the path from power-on to a
  kernel finding its root device.

`bus::pci`'s `CONFIG_SPACE_LEN` is still 256 bytes. The ECAM window decodes the
full 4 KiB and answers **zero** above `0xff`, which is not a stub: an all-zero
Extended Capability header at `0x100` is the defined encoding for *this function
has none*, so a traversal terminates correctly. Widening `CONFIG_SPACE_LEN` is
the seam when a function grows a real extended capability.

### The ACPI tables are generated, not written

[`src/dev/q35/acpi.rs`](../../src/dev/q35/acpi.rs) walks the realized machine and
reads every address out of it, the way
[`riscv-virt.md`](riscv-virt.md)'s device tree generator does. Nothing in that
file writes an address down:

| Table field | Where it comes from |
| --- | --- |
| `MADT` local APIC address | the base of the mapping whose region is the local APIC's |
| `MADT` local APIC ID | a **debug read** of that APIC's own ID register |
| `MADT` I/O APIC address | the base of the I/O APIC's mapping |
| `MCFG` base and bus range | the mapping the (G)MCH made for `PCIEXBAR` |
| `FADT` `PM1a_EVT_BLK`, `PM1a_CNT_BLK`, `PMTMR_BLK`, `GPE0_BLK` | the mapping the LPC made for `PMBASE`, plus ICH9 Table 13-11's offsets |
| `HPET` address and block ID | the HPET's mapping, and a debug read of its capabilities register |
| every table's own address | where the machine file mapped the generator's region |

`tests/q35_board.rs` proves the claim rather than asserting it: it moves the
ECAM window with a guest configuration write, regenerates, and checks that the
`MCFG` followed.

**Three things are declared** on the `acpi` object, each with the reason beside
it in the machine file: the processor count (a processor is not a region in any
address space, and `core::device` keeps `Any` out of its supertrait chain — the
same limitation `riscv::dt::CpuSpec` documents for harts), the I/O APIC's ID
(reaching it means writing its index register, which a debug read may not do),
and the SCI's interrupt (it is `ACPI_CNTL[2:0]`'s choice, made after the table
is written).

## What it was measured doing

`tests/q35_board.rs` is gated on `RSEMU_BIOS`, so `cargo test` stays hermetic;
point it at a current prebuilt PC firmware and the board reaches that firmware's
**boot prompt**. Everything below is a byte the guest wrote to its own log port
at `0x402`, which is reading what a program printed and nothing more
(`../../ROADMAP.md` §1 — the image is run, never read, and never vendored):

```text
RamSize: 0x040c0000 [cmos]
Relocating init from 0x000e9620 to 0x030b5300 (size 44128)
=== PCI bus & bridge init ===
=== PCI device probing ===
Found 3 PCI devices (max PCI bus is 00)
PCIe: using q35 mmconfig at 0xb0000000
PCI: init bdf=00:00.0 id=8086:29c0
PCI: init bdf=00:02.0 id=1234:1111
PCI: init bdf=00:1f.0 id=8086:2918
Q35 LPC init: elcr=00 0c
PCI: Using 00:02.0 for primary VGA
Turning on vga text mode console
Found 0 lpt ports
Found 1 serial ports
PS2 keyboard initialized
Press ESC for boot menu.
```

Four of those lines are claims about *this* work, and the test asserts each
rather than admiring it:

* **`PCIe: using q35 mmconfig at 0xb0000000`** — the firmware recognised the
  chipset, wrote `PCIEXBAR` itself to an address neither the board nor the test
  chose, and enumerated through the window that write created. Everything after
  that line came through ECAM.
* **`Relocating init`**, and `PAM0`-`PAM3` reading `0x33333330` afterwards — it
  shadowed itself into the DRAM the registers at `0x90`-`0x96` switch into view.
* **`Q35 LPC init`** — it found the south bridge at `00:1f.0` and ran the
  initialisation it keeps for that part, which is also the only evidence
  available that the ICH9 device identification below is the right one.
* A complete POST: the BDA filled, a text console, a keyboard, a timer tick
  still counting.

One thing it does **not** show: it does not boot an operating system, because
there is no bootable medium in that test. What it also does not show is
anything about long mode — a legacy PC firmware never leaves real and 16-bit
protected mode, so it exercises the chipset rather than the processor. That is
what the hermetic test below is for.

It also reported `RamSize` as 64 MiB + 768 KiB on a board configured with
128 MiB. That was `pc.rtc`, not the firmware: the CMOS saturated the kilobyte
pair at 0xff00 and left the 64 KiB-block pair at `0x34`/`0x35` empty, so
`65280 * 1024 + 0` plus the megabyte below is `0x040c0000` exactly. The two
pairs are a partition — the kilobytes to 16 MiB, the blocks above it, the same
split `INT 15h AX=E801h` reports — and `pc.rtc` now does that split itself from
a single `extmem`. The arithmetic is asserted in `dev::pc::rtc`'s own tests; the
number above is what the old encoding produced and is left here as the record of
it.

rsemu's **own** firmware also POSTs on this board and boots a guest off the IDE
drive; those two tests are hermetic and always run.

### A guest reaches long mode, and says so down COM1

The third test that is hermetic and always runs, and the one that measures the
processor rather than the chipset —
`a_guest_reaches_long_mode_and_prints_through_com1_on_this_board`. rsemu's own
BIOS POSTs, `INT 19h` reads a boot sector off the IDE drive and jumps to it,
and that sector does the rest itself:

```text
q35 long mode: stopped at 0008:00007d93, halted=true, 221201 cycles
  |q35: real mode|
  |LONG64|
```

Both lines came out of the 16550 at `0x3f8` and were read off the host end of
the character port, so the serial port is proven by the same run that proves
the processor. Between them the sector builds a PML4, a PDPT and a page
directory identity-mapping the first 4 MiB with 2 MiB pages, sets `CR4.PAE`,
loads `CR3`, sets `EFER.LME`, writes `CR0.PG|PE` and far-jumps into a
descriptor with `L` set (SDM Vol. 3A §9.8.5).

`LONG64` is printed by hand-encoded 64-bit instructions, and the assertion that
makes the claim honest is not the string: it is a marker at `0x510` stored by
`mov r8, imm64` / `mov [abs], r8`. `R8` does not exist outside 64-bit mode, so
a processor that had not entered it would decode those bytes as something else
and leave the marker absent. `CS` reading `0008` at the halt — the 64-bit code
selector, not the real-mode `f000` every other test on this board ends in — is
the same fact from the other side.

What it does **not** show is an operating system. It is eight instructions of
64-bit code, not a kernel; what it settles is that nothing between the reset
vector and long mode is missing on this board.

### The device identification is a label, and the board says so

Datasheet §5.1.2 gives three identifications for one part family — `29B0h` for
the 82Q35, `29C0h` for the 82G33/82P35, `29D0h` for the 82Q33 — and Table 5-1
prints `29C0h` as the register map's own default. With `29B0h` the firmware
above does not recognise the bridge at all and stops eighty thousand cycles in:

```text
Unable to unlock ram - bridge not found
RamSize: 0x00000000 [cmos]
```

So `machines/q35.machine` writes `device-id = 0x29c0` and explains itself where
a reader will meet it. Every register modelled here is common to the family, so
this is a label rather than a different part.

## Where the tables live, and why that is temporary

`machines/q35.machine` maps them at `0xe0000`, inside ACPI §5.2.5.1's own RSDP
search window, and the BIOS socket is 64 KiB at `0xf0000` rather than `pc-at`'s
128 KiB at `0xe0000` to make room.

**On a real machine the firmware would allocate this and report it in E820 as
ACPI reclaim memory.** That is where this should end up: `acpi::generate` is a
free function precisely so that `src/fw/pcbios` can call it and stage the bytes
itself, at which point the `q35.acpi` device and its `map` statement go away.
The seam is `generate` plus `MachineFacts`.

One consequence to know about: a *third-party* firmware that programs the PAM
registers to shadow `0xe0000` hides these tables behind its own DRAM — and it
should, because it would be publishing its own. rsemu's own BIOS does not touch
PAM, so on the default board they stay visible.

## Known gaps, in the order they matter

1. **SMP.** One processor, one local APIC, and a MADT that says `cpus = 1`.
   This is now the whole distance between the board and phase 6b's gate, and
   it is a board change rather than a core one: a second `cpu.x86`, a second
   `pc.lapic`, and the start-up IPI path between them. The processor itself is
   an `x86-64` — long mode, PAE, the four-level walk, NX, SYSCALL, x87, SSE and
   SSE2 — and the board proves it is reachable rather than asserting it.
2. **`_PRT`, but only the fixed form.** The routing itself is complete: a PCI
   function drives an `INTA#`-`INTD#` pin (`bus::pci::Intx`), the fabric rotates
   it by device number onto one of four nets (`bus::pci::swizzle`), the bridge
   collects those nets as `PIRQ[A-D]`, and the DSDT carries a `_PRT` generated
   from the routing registers the bridge is actually holding.
   `tests/q35_intx.rs` runs the whole path with a guest that reprograms the
   router mid-interrupt. What the `_PRT` cannot do is describe a router the
   *guest* reprograms after the tables were written: the other form of `_PRT`
   names PCI link devices, and a link device needs `_PRS`, `_CRS`, `_SRS` and
   `_DIS` — four AML methods, which `q35::aml` deliberately cannot encode. So
   the board states its power-up routing (`pirq-routes`), the table is generated
   from it, and a firmware that wants to move it publishes its own tables.
3. **`_CRS` on the host bridge.** The DSDT names `PNP0A08`/`PNP0A03` and its
   `_ADR`, `_UID` and `_BBN`, but declares no resource template — no bus number
   range, no I/O or memory aperture, no ECAM window. An operating system takes
   those from `MCFG` and from its own probing when they are absent.
4. **SMM.** `SMRAM`, `ESMRAMC` and `TSEGMB` are not modelled and read as their
   reset values. SMM is how a q35's firmware protects itself, so a firmware that
   relies on it will find nothing happening — though, measured, the one above
   does not need it to reach a boot prompt, so this is lower down the list than
   it looks.
5. **`S5`.** `SLP_TYP` and `SLP_EN` are modelled as registers and the request is
   latched, but writing `111b` does not switch the machine off: the seam a
   guest's power request lands on is `dev::riscv::syscon`'s `signals` host
   object, behind a feature this board has nothing to do with. Moving that seam
   to `core::hosts`, beside the character ports, is the fix.
6. **The ICH9's device identification is a documented gap.** §13.1.2 does not
   give one — it defers to the Specification Update (316973), which could not be
   retrieved from any public mirror — so `q35.lpc` makes `device-id` a
   **required** property with no default and the machine file states the number
   with that caveat attached. Nothing functional depends on it: software finds
   the chipset by class code `060100h` and its ACPI hardware through the FADT.
7. **`MCFG`'s layout is the one table not read from its own specification.** It
   is defined in the PCI Firmware Specification revision 3.0 §4.1.2, Tables 4-2
   and 4-3, which is members-only at PCI-SIG; the layout implemented is the
   OSDev wiki's, corroborated against the Ubuntu Firmware Test Suite's `mcfg`
   reference. Weaker than every other citation here, and flagged rather than
   smoothed over.

## Two windows, two routes, and the rule between them

Worth knowing before debugging this board, because it is unintuitive and it is
tested both ways in `tests/q35_board.rs`.

A configuration write that moves a window can only retopologise a space **the
access is not already travelling through** — `src/bus/pci/bar.rs` states the
rule and `src/core/space.rs` is where the try-lock lives. A q35 has two routes to
configuration space, in two different address spaces, so:

* a `PAM` or `PCIEXBAR` write through **`0xcfc`** moves a memory-space window
  from inside an I/O-space access, and lands at once;
* a `PMBASE` or `ACPI_CNTL` write through **ECAM** moves an I/O-space window
  from inside a memory-space access, and lands at once;
* either one through the *same* space sets a `stale` flag instead.

A 440FX never met the third case, because it has only one route and that route
is always in the other space. Here the retry cannot be another configuration
access, so **the (G)MCH takes a clock domain** and asks the scheduler for a tick
while it owes a retopology; `Device::advance_to` runs from the run loop with no
access in flight, which is the only moment a topology guard is actually
available. `machines/q35.machine` gives it the front-side-bus oscillator, which
is what a (G)MCH is clocked by anyway.
