# Motorola 680x0

Sources for `src/cpu/m68k` — an MC68000 interpreter with a modelled prefetch
queue; the MC68010, MC68020, MC68EC020, MC68030, MC68EC030, MC68040,
MC68LC040 and MC68EC040 as `model`s of it; and the MC68881 and MC68882
floating-point coprocessors, and the MC68040's on-chip unit, as an `fpu`
property, and — on a 68000 — an **IR frontend** and the two translated
engines `engine = "jit"` and `engine = "jit-host"` select, which have a section
of their own below. Everything here
is Motorola's own documentation or a test corpus that is fetched and never
vendored; the exclusions at the bottom are the part that matters most.

## The 68010, as modelled

| | 68000 | 68010 | Where it is written down |
| --- | --- | --- | --- |
| vector table | at zero | at `VBR` | M68000UM §6.2.1 |
| group 1/2 frame | 6 bytes | 8 bytes, format `$0` | Figure 6-6 |
| bus/address error frame | 14 bytes | 58 bytes, format `$8`, 26 words written | Figure 6-8 |
| `RTE` | pops six bytes | reads the format word; format error (vector 14) on one it does not know | §6.4 |
| `MOVE from SR` | unprivileged, reads its destination first | privileged, no read | PRM Table A-1 note 4; M68000UM Table 9-18 |
| `CLR`, `Scc` to memory | read, then write | write only | Tables 9-9, 9-10 |
| new instructions | — | `MOVEC` (`SFC`, `DFC`, `USP`, `VBR`), `MOVES`, `RTD`, `MOVE from CCR`, `BKPT` | PRM Section 4 and 6 |

Two things are deliberately not the 68010's:

- **Returning from a bus or address error restarts the instruction** instead
  of continuing it from saved microcode state, which this interpreter does not
  have. The frame's internal words — which the manual leaves to the processor —
  carry the instruction's address and the old values of any address register
  it had already stepped, and `RTE` puts those back, so the result is the one
  continuation would have given. A cycle the handler completed in software
  (the rerun flag set in the special status word) is honoured: the restarted
  instruction takes that one access from the frame's data input buffer. A
  version number of this core's own sits where the manual puts one, and `RTE`
  refuses anyone else's.
- **Timing is the 68000's**, per bus access, with the 68010's removed reads and
  added format-word writes — which makes the exception times of MC68000UM Table
  9-19 come out as published. The 68010's faster `MULU`/`DIVU` and some branch
  times (Tables 9-6, 9-15) and **loop mode** are not modelled. Loop mode is
  timing only: a one-word instruction repeated by the `DBcc` after it runs from
  the queue with only its operand cycles on the bus.

`BKPT` runs a breakpoint-acknowledge cycle in CPU space. `MemAttrs` carries no
function code, so nothing can answer it; it ends as an unanswered one does, in
an illegal-instruction exception through vector 4.

## The 68020, as modelled

Implemented, with the manual section the behaviour comes from:

| | |
| --- | --- |
| address pins | 32 on the 68020, 24 on the 68EC020 — the only difference (MC68020UM §1) |
| alignment | operands at any address; an address error only for an instruction fetched from an odd one (§6.1.3) |
| addressing | the scaled brief format and the full format — base and outer displacements, suppression, memory indirection pre- and post-indexed (PRM §2.2.3, Table 2-2); a reserved full-format word is an illegal instruction |
| instructions | `MULS.L`/`MULU.L` (32 and 64-bit), `DIVS.L`/`DIVU.L`/`DIVSL.L`/`DIVUL.L`, `BFTST`/`BFEXTU`/`BFEXTS`/`BFFFO`/`BFSET`/`BFCLR`/`BFCHG`/`BFINS`, `CAS`, `CAS2`, `CHK2`, `CMP2`, `CHK.L`, `PACK`, `UNPK`, `EXTB.L`, `LINK.L`, `TRAPcc`, `Bcc.L`/`BRA.L`/`BSR.L`, `CALLM`/`RTM`, and `TST`/`CMPI` on the extra modes |
| registers | `MSP`, `ISP` and the **M** bit; **T0**, trace on change of flow; `CACR`, `CAAR` through `MOVEC` |
| frames | `$0`, `$1` (throwaway), `$2` (six words), `$A` (short bus fault), `$B` (long bus fault), byte for byte as Table 6-5; `$9` needs a coprocessor and is never built |
| coprocessor | none: every F-line word takes the line-F exception, `cpSAVE`/`cpRESTORE` in user state first take a privilege violation (§7.5.2) |
| prefetch faults | deferred until the word is used (§6.1.2): running up to the last word of mapped memory does not fault |

Not implemented, and what happens instead:

- **The instruction cache's contents.** `CACR`'s **E** and **F** are kept;
  clear and clear-entry have nothing to clear. Every fetch goes to memory, and
  the cache has no effect on timing.
- **Continuing a faulted instruction.** As on the 68010, `RTE` from a format
  `$B` frame restarts the instruction, with the address registers it had
  stepped put back from the frame's internal words; a data cycle the handler
  completed (DF cleared) is replayed from the data input buffer, and a
  read-modify-write it completed (RM set, DF cleared) is stepped over.
- **CPU space**, so `CALLM` with a type 1 descriptor is a format error — the
  manual's outcome for access-control hardware that does not answer (§9.8) —
  and `BKPT` is an illegal instruction.
- **Dynamic bus sizing to a 32-bit port.** Operands are driven sixteen bits at
  a time, as to a 16-bit port.
- `CHK2`/`CMP2`'s comparison is specified by the manual only for a signed
  pair with the arithmetically smaller bound first and an unsigned pair with
  the logically smaller first. The core uses a single modular test that gives
  both; an inverted pair gives whatever that test gives.

### Timing: the cache-case column

MC68020UM §8.2 gives every time three ways. The core charges the **cache
case**: the instruction in the cache, no overlap with its neighbours. The best
case depends on how much of the *adjacent* instructions overlaps this one,
which the tables do not give; the worst case assumes the cache off, which is
not how the software the 68020 was built for runs. The cache case is a property
of the instruction alone and has no instruction-fetch cycles in it, so nothing
about the unmodelled cache enters it.

The time is charged per instruction from the tables — the instruction's row
plus the effective-address table its footnote names, or the complete `MOVE`
table — and is the same every time. The manual is explicit that exact 68020
timing cannot be computed from these tables at all (Tables 8-2 and 8-3); what
this gives is a consistent, documented approximation between the published
bounds. `src/cpu/m68k/timing.rs` lists the few places the tables are silent
and what is charged there. The one discrepancy found in the manual itself: its
worked example charges `BFCLR $6000{0:8}` the *fetch* immediate row where the
bit-field table's footnote says *calculate*; the core follows the footnote.

Two places the manual does not settle, and the reading taken:

- **The limit check at the root.** §9.7.1 says a root pointer with `DT = $1`
  is limit-checked "regardless of the state of the FCL bit"; Figure 9-28
  returns without checking when `y = 'RP'` and `FCL = 1`, and §9.7.2's
  description of **FCL** agrees with the flowchart. The core follows the
  flowchart.
- **The ATC replacement policy** is "pseudo least recently used" and is not
  published. The core fills an invalid entry first and otherwise cycles
  round-robin. Visible only through `PTEST` level 0 after twenty-two pages.

entry, but there is no cache and no pin), `MMUDIS` (no such input; `TC`'s
**E** bit is the switch), `RMC` across a search (the core holds its own bus
lock for the whole instruction, which is stronger), and burst descriptor
fetches. A table search's own bus cycles *are* driven, logged and charged.

## The 68040, as modelled

Three packages: the MC68040, the MC68LC040 without a floating-point unit,
and the MC68EC040 without that or the paged memory management unit (M68040UM
Appendices A and B). All three keep the full 32-bit address bus, so unlike
the 68EC020 none of them is a 24-bit part.

**The 68040 is not a 68030 with additions**, and the code says so: `has_030()`
is false on it. The coprocessor interface is gone (§1.1), and with it the
68030's `PMOVE`, `PLOAD`, `PTEST` and `PFLUSH`, which travelled over it; the
memory management unit is a different design reached through `MOVEC`; and
`CAAR` is gone too — M68000PRM §6, *MOVEC*, note 2 makes `$802` "for the
MC68020 and MC68030 only".

| | |
| --- | --- |
| instructions | the 68030's, plus `MOVE16`, `CINV`, `CPUSH` and the 68040's own `PFLUSH`/`PTEST`; less the 68030's MMU encodings and the coprocessor interface |
| address pins | 32 on all three packages |
| `CACR` | two bits: **DE** at 31 and **IE** at 15 (§4.2, Figure 4-4). The 68020's and 68030's clear-the-cache bits are gone — `CINV` and `CPUSH` do that job now |
| `MOVEC` | adds `TC`, `ITT0`/`ITT1`, `DTT0`/`DTT1`, `MMUSR`, `URP` and `SRP`; drops `CAAR`. An MC68EC040 has only the four transparent translation registers, which it calls `IACR0`/`IACR1` and `DACR0`/`DACR1` |
| frames | `$0`, `$1`, `$2`, `$3` and `$7`. An **address error** is format `$2` where a 68020 pushed `$A`; everything else is the thirty-word format `$7` access error frame (§8.4). `$A` and `$B` are refused by `RTE` |
| timing | **the 68020's table**, as for the 68030, with M68040UM §10.3's own numbers for `CINV` and `CPUSH` — the only rows in `timing.rs` that come from this manual, because there is no 68020 instruction to borrow from. `MOVE16` has a row in neither manual and is charged the accesses it drives; `PFLUSH` and `PTEST` are charged eight clocks plus a table search's own cycles, as the 68030's `PMOVE` is |

### `MOVE16`

Both addresses are used with their low four bits ignored — "the lines are
aligned to 16-byte boundaries" — and an address register in the postincrement
mode steps by **sixteen from the value it held**, so the manual's own example
(`A0 = $1400F`) reads the line at `$14000` and leaves `$1401F` behind
(M68000PRM §4). One register named on both sides steps once and the line is
copied over itself (M68040UM Table 1-4, note 7).

Hardware makes the transfer as a burst read and a burst write that begin at
the long word the effective address actually names. This core has no burst:
it reads four long words in ascending order from the aligned base and writes
them the same way. The sixteen bytes that land are the same; the order they
cross the bus in is not.

### The caches, and what "not modelled" means here

This core has no instruction or data cache: every access goes to memory and
nothing is ever held. **That is a copyback cache that never holds a dirty
line**, which is a legal state for the hardware to be in and the one `CINV`
and `CPUSH` are defined against:

- `CINV` "invalidates selected cache lines"; there are none, so there is
  nothing to invalidate, and "any dirty data in data cache lines that
  invalidate are lost" loses nothing.
- `CPUSH` pushes dirty lines and then invalidates; with no dirty line
  anywhere, M68040UM Table 10-4's **best case** — "a cache containing no
  dirty entries" — is what happens every time, and that is the time charged.

So both are no-ops that cost time, and the guest-visible result is right:
memory already holds everything a push would have written, and a later read
already sees everything an invalidate would have exposed. The address
register a line or page operation names is read as a *physical* address and
makes no bus cycle, so nothing there can fault.

What is *not* modelled is the cache's effect on **timing** and on the **bus
trace** — the same thing already recorded against the 68020's and the
68030's caches — and the cache *modes*. `CM`, `U1` and `U0` are read out of
the descriptors and the transparent translation registers, accumulated into
the ATC entry and reported by `PTEST`, but there is no `UPA1`/`UPA0` pin to
drive and no cache to switch between write-through and copyback.

The ATC entry's data half is laid out as an `MMUSR` value on purpose: Figure
3-6 and Figure 3-21 name the same fields, so `PTEST` reports by copying and
the two cannot drift apart.

Not modelled:

- **Two address translation caches.** The instruction and data memory units
  have one each (§3.3). One is kept, and the merge is unobservable: the
  tables are shared (§3.2.1), every `PFLUSH` variant invalidates entries "in
  **both** the instruction and data address translation caches" (M68000PRM
  §6), and only `PTEST` reads an entry — and it rewrites the one it reports
  on. The split that *is* observable, the instruction and data transparent
  translation registers, is modelled in full.
- **The replacement algorithm.** §3.3 calls it pseudo-random and publishes
  only that "a 2-bit counter, which is incremented for each ATC access,
  points to the entry to replace". This fills an invalid way first and
  otherwise cycles a two-bit counter *per install* rather than per access.
  Visible only through `PTEST` after more than four pages in one set.
- **`MDIS`**, burst descriptor fetches, and the `LOCK` the read-modify-write
  history updates of Table 3-1 assert. A table search's own bus cycles *are*
  driven, logged and charged.

### The access error frame, and restart

An address error takes a **format `$2`** frame carrying the referenced
address with bit 0 cleared (§8.2.2, §8.4.3). Everything else takes the
thirty-word **format `$7`** frame of §8.4.6, written field by field, with the
special status word of Figure 8-7. Its `ATC` bit distinguishes a translation
failure — "a nonresident entry (bus error during table search or invalid
descriptor encountered) or privilege violation (write protected or supervisor
only)" — from a physical bus error (§8.4.6.2); a transparently translated
block's write protection is counted with the former, because it is not a bus
error and Figure 3-22 takes the same "abort cycle, take access error
exception" exit for it.

The `TT`/`TM` pair needed two rules. An ordinary access drives its own
function code, so an instruction fetch keeps `$2` or `$6` — §8.4.6 leans on
exactly that. A `MOVES` is converted: program space folds onto data, and a
function code outside the four ordinary ones becomes an alternate logical
access with `TT = 10` (§3.2.5, Table 3-2).

**All three write-back status bytes are written invalid.** This interpreter
has no write-back pipeline and no cache, so nothing is ever pending — and
that is the first row of Table 8-6, "All Read Access Errors ... WB1S 0, WB2S
0, WB3S 0, Easy Cleanup: None". A conforming handler checks the `V` bits,
does nothing and returns. `RTE` then **restarts the instruction**, which is
the same bargain this core makes on the 68010 and the 68020 and is what
§8.2.1 describes anyway: the stacked PC is "the logical address of the
instruction executing at the time the fault was detected". The address
registers a partly executed instruction had stepped are put back from the
write-back fields the invalid status bytes told the handler to ignore.

An `RTE` from a format `$7` frame with one of the four continuation bits set
is a **format error**. Those cases hand the work to microcode this core does
not have, and §8.4.6.7 already says a handler that sets more than one leaves
`RTE` undefined.

### The floating-point unit

`fpu = "68040"` on an MC68040, and it is the default there and the only legal
value: the unit is on the chip and there is no way to switch it off, so the
part without one is the `68lc040`. A 68881 or 68882 cannot be attached to any
68040 — there is no coprocessor interface to attach it to (§1.1).

**It implements ten operations in hardware and traps for the rest.** That is
the whole shape of it, and the opposite choice was available: this core
computes all eighteen transcendentals correctly rounded and could have
answered `FSIN`. It does not, because a 68040 does not, because an A4000's
Kickstart installs a software package precisely because it does not, and
because a core that quietly succeeds where the hardware traps is a core whose
guests behave differently from the machine they were written for.

| | |
| --- | --- |
| hardware | `FABS`, `FADD`, `FCMP`, `FDIV`, `FMOVE`, `FMUL`, `FNEG`, `FSQRT`, `FSUB`, `FTST`, and the `FSxxx`/`FDxxx` forms of the eight that produce a result |
| also hardware | `FBcc`, `FDBcc`, `FScc`, `FTRAPcc`, `FNOP`, `FMOVEM`, `FMOVE` to and from the control registers, `FSAVE`, `FRESTORE` |
| unimplemented | the other twenty-nine, `FMOVECR` and `FSINCOS` included: vector 11 with a format `$2` frame |
| unsupported data type | packed decimal: vector 55, format `$0` for opclass 000 and 010 and format `$3` for the `FMOVE` out of opclass 011 |

The `FSxxx`/`FDxxx` forms "specify single- and double-precision rounding
regardless of the precision specified in the FPCR PREC bits" (§9.4.2), and
like `PREC` itself the forced precision shortens the exponent range as well
as the significand — the point of it is to match a device that does not
support extended precision at all (§9.4).

The unimplemented-instruction exception is taken properly rather than merely
taken:

- The frame is **format `$2`**, which is how a handler tells an unimplemented
  floating-point instruction from an F-line *illegal* one, since the two
  share a vector and only the frame separates them (§9.6.1). The stacked PC
  is the **next** instruction's, so an emulation handler returns straight
  into the program.
- The effective address is calculated and the source operand fetched
  **before** the trap, because §9.6.1 says they are: a postincrement has
  happened by the time the handler runs, and the address is in the frame.
- `FSAVE` then writes the **twenty-six-word unimplemented instruction state
  frame** of Figure 9-10(d), field by field: `CMDREG1B` at `+$10`, `STAG` and
  `DTAG` in bits 31–29 of `+$0C` and `+$14`, `E1` at bit 26 and `T` at bit 20
  of `+$18`, and `FPTEMP` and `ETEMP` in the 96-bit extended layout at `+$1C`
  and `+$28`. The operands go in **unmodified**, denormals and unnormals
  included, because "the floating-point instruction emulation routine must
  detect the unsupported data type" and cannot if the unit has already
  normalized it away (§9.6.1, §9.6.2).

Which instructions are unimplemented needed a decision, because the manuals
disagree. M68040UM Table 9-10 omits `FLOG2`, `FSGLMUL` and `FSGLDIV`;
M68000PRM Table A-1 marks all three with the same "emulated in software"
footnote it gives the twenty-six the other table lists. **Table A-1 wins**: it
is the self-consistent superset, and `FLOG2` is no more implementable in that
hardware than the `FLOGN` beside it.

What differs from a real 68040's unit:

| | |
| --- | --- |
| **denormalized and unnormalized operands** | computed, not trapped. A real 68040 raises vector 55 so software can do what `src/float` already does correctly; a guest whose package is never called gets the same values. This is the one divergence, and it is the only place this core is *more* capable than the part |
| **`FSAVE` frames** | three of the four: null, idle — four bytes, which is the whole frame on this part — and the twenty-six-word unimplemented instruction frame. The fifty-word **busy** frame is pipeline state this core never has, so a frame claiming to be one is a format error rather than a guess. §9.7 says an unsupported data type produces a busy frame while Table 9-16 lists the unimplemented frame's fields for it; this follows Table 9-16, because those are the fields it can fill |
| **arithmetic exceptions** | reported at the instruction that caused them, as for the 68881 — the same post-instruction bargain already in this file, and the reason `E3` and the write-back temporaries in the state frame are always zero |
| **transcendental accuracy** | does not arise: they are not computed |


## The floating-point coprocessor, as modelled

`fpu = "68881"` or `"68882"` on a 68020 or a 68030; `none` is the default and
`none` on a 68000 or 68010 is the only setting, since the F-line coprocessor
interface starts at the 68020 (MC68020UM §7) and ends with it — the 68040 has
none, and its own unit is *The floating-point unit* above.

| | Where it is written down |
| --- | --- |
| registers | `FP0`–`FP7`, `FPCR`, `FPSR`, `FPIAR`, every field (§2). Condition codes by result *data type*, Table 2-1; the five accrued equations, §2.3.4 |
| formats | byte, word, long, single, double and the 96-bit extended (§3, Table 3-3). **Packed decimal is not implemented** |
| moves | `FMOVE` both ways, `FMOVEM` in both list orders and both dynamic forms, `FMOVE(M)` for the control registers, `FMOVECR`'s whole ROM (§4) |
| conditionals | `FBcc`, `FScc`, `FDBcc`, `FTRAPcc`, `FNOP`, all 32 predicates, `BSUN` as a pre-instruction exception (M68000PRM Table 3-23; M68881UM §4) |
| arithmetic | `FADD`, `FSUB`, `FMUL`, `FDIV`, `FSGLMUL`, `FSGLDIV`, `FABS`, `FNEG`, `FSQRT`, `FINT`, `FINTRZ`, `FGETEXP`, `FGETMAN`, `FSCALE`, `FMOD`, `FREM`, `FCMP`, `FTST` |
| transcendentals | all eighteen: `FSIN`, `FCOS`, `FTAN`, `FSINCOS`, `FASIN`, `FACOS`, `FATAN`, `FSINH`, `FCOSH`, `FTANH`, `FATANH`, `FETOX`, `FETOXM1`, `FTWOTOX`, `FTENTOX`, `FLOGN`, `FLOGNP1`, `FLOG2`, `FLOG10` |
| exceptions | the eight classes, the seven vectors (48–54), the enable/exception/accrued bytes, and the trap-enabled results of §6.1.2 to §6.1.7 |
| context | `FSAVE`/`FRESTORE`, null and idle frames |

All of it is computed in `src/float`, which is integer arithmetic rounded
once — never host floating point, so a guest's results are identical on every
host and in a browser (`ROADMAP.md` §9.1).

### The extended format is x87's value encoding, and four other things

`src/float/x87.rs` implements the same 80-bit format with an explicit integer
bit that the 68881 uses, and the *values* agree bit for bit. Four things do
not, and each is handled in `src/cpu/m68k/fpu.rs` rather than by bending a
shared module to one guest:

| | 68881 | x87 |
| --- | --- | --- |
| in memory | **96 bits**, big-endian: exponent word, a word of zeros, then the significand (Table 3-3) | 80 bits, little-endian |
| non-zero exponent, integer bit clear | an **unnormalized number**, normalized before use (§3.5.1) | an *unnormal*: unsupported, invalid operation (SDM Vol. 1 §8.2.2) |
| maximum exponent, integer bit clear | an ordinary infinity or NaN (Figure 3-6, §3.2.5) | pseudo-infinity / pseudo-NaN: unsupported |
| the NaN it creates | all-ones mantissa (§3.2.5) | the indefinite: negative, zero payload |

`canonical()` settles the middle two on the way in and `generated_nan()` the
last on the way out. A fifth difference is in the rounding *precision* rather
than the format: `FPCR`'s **PREC** shortens the exponent range as well as the
significand (§2.2.2), where x87's `PC` shortens only the significand — which
is why `src/float/x87.rs` grew `add_to`/`sub_to`/`mul_to`/`div_to`/`sqrt_to`/
`round_to`, taking the format parameters directly.

The manual does not give the sign of the NaN the unit creates. This core uses
a **positive** one, `$7FFF FFFFFFFFFFFFFFFF`.

### Accuracy: better than the part, deliberately

M68881UM §4.3.2 bounds the part's own transcendentals at "one unit in the last
place of double precision (which is equal to **4096 units in the last place of
extended**)", typically **64**; and §4's *FCOS* adds that "large arguments may
lose accuracy during reduction, and very large arguments (greater than
approximately 10^20) lose all accuracy". A bound that loose is not something
to reproduce, and nothing short of that part's microcode could reproduce its
exact error pattern. So `transcend.rs` computes the functions properly:

- every intermediate is a **128-bit significand**, rounded to the destination
  exactly once;
- the trigonometric reduction is **Payne–Hanek against 16 640 bits of 2/π**,
  exact for every representable extended argument.

**Measured**: `tests_transcend.rs` holds 133 `(argument, result)` pairs
computed by **GNU `bc -l` at `scale=110`** — a different implementation, in a
different language, at about ninety correct decimal digits against the
nineteen an extended significand holds — rounded once by exact rational
arithmetic. All 133 come back with the same bits: correctly rounded, not
merely within an ulp. The test's module documentation has the `bc` programs,
so the table can be regenerated and checked.

### What differs from a real 68881, and why

| | |
| --- | --- |
| **Packed decimal** | not implemented; the `011` source specifier and the `011`/`111` destination formats take the line-F exception, which is what a 68040 does for that format ("this encoding will cause an unimplemented data type exception ... to allow emulation in software", M68000PRM §5) |
| **The coprocessor interface** | a 68881 is a device in CPU space reached through coprocessor interface registers (§7). `MemAttrs` carries no function code, so nothing here can answer a CPU-space cycle; the instructions are executed directly. The bus trace of a floating-point instruction is therefore not the hardware's |
| **Concurrency** | a real coprocessor runs beside the main processor, so an arithmetic trap with a register destination arrives **pre-instruction on the next floating-point instruction** (§6.1.3). Here it is post-instruction on the instruction that caused it. Same vector, same `FPIAR`, same `FPSR`; the stacked program counter is one instruction earlier |
| **Execution time** | the main processor's work only — the effective-address time and the transfer. M68881UM §8 tables the coprocessor's own in *its* clocks. In the conformance ledger |
| **Transcendental accuracy** | better than the part, as above. Software that depended on a 68881's exact low bits will see different ones |
| **`FSAVE` frames** | the right *lengths* — 28 bytes on a 68881, 60 on a 68882 — and the null frame for an untouched unit, but the body is this core's own, since the hardware's is microcode state. The version byte is its own too and `FRESTORE` refuses anybody else's, the same bargain the 68010's long bus-fault frame makes |
| **`FATANH(±1)`** | §6.1.6's sentence names `+infinity` for a source of `-1` and `-infinity` for `+1`, which is the opposite of the function's own limits. This core returns `+infinity` for `+1` |

## The IR frontend and the translated engines

`src/cpu/m68k/lift.rs` lifts MC68000 guest instructions into `ir::Block`s and
`src/cpu/m68k/engine.rs` runs them on `jit::Dispatcher`; `engine = "jit"` and
`engine = "jit-host"` on `cpu.m68k` select it, behind `cpu-m68k-lift` plus
`jit`. The two differ in the backend: `jit` executes a block on the portable
`ir::Interp`, which runs anywhere the crate does, and `jit-host` compiles it
with `jit::x86` or `jit::arm64` and falls back to the portable one for anything
a code generator refuses. It is the **fourth** frontend for the translation IR,
after RISC-V, x86 and A64, and the first for a core whose interpreter is
bus-accurate to the cycle.

CLAUDE.md, *CPU cores*, is the contract: **the interpreter is the oracle**, and
the frontend is differentially tested against it forever.
`src/cpu/m68k/differential.rs` is that harness and it compares whole cores —
`engine = "interp"` against each translated engine on two identical address
spaces —
on the registers, `SR` (the **X** bit included), the program counter, **both
prefetch words**, the cycle counter, the scheduler's debt, the halted and
stopped flags, the bus-fault count and its address, and every byte of RAM,
after every unit.

### What is lifted

Across all twelve addressing modes, on a 68000 only:

| Group | Encodings |
| --- | --- |
| moves | `MOVE`, `MOVEA`, `MOVEQ`, and the memory-to-memory forms — `MOVE.B/W (An)+,(Am)+` and the rest |
| arithmetic | `ADD`, `ADDI`, `ADDQ`, `SUB`, `SUBI`, `SUBQ`, `ADDA`, `SUBA`, `ADDX`, `SUBX`, `NEG`, `NEGX` |
| compares | `CMP`, `CMPI`, `CMPA`, `CMPM`, `TST` |
| logic | `AND`, `ANDI`, `OR`, `ORI`, `EOR`, `EORI`, `NOT`, `CLR` |
| shifts and rotates | `ASL`, `ASR`, `LSL`, `LSR`, `ROL`, `ROR`, `ROXL`, `ROXR` — at a **static** count, and the one-bit memory form |
| bit | `BTST`, `BSET`, `BCLR`, `BCHG`, with a static bit number into a register and either kind into memory |
| control flow | `Bcc`, `BRA` (byte and word displacement), `DBcc`, `Scc` (memory on any condition, a data register on `ST`/`SF` — reason 3 below), `JMP`, `RTS` |
| registers | `EXT`, `SWAP`, `EXG`, `LEA`, `UNLK`, `NOP` |
| condition codes | `MOVE from SR`, `MOVE to CCR`, `ORI/ANDI/EORI to CCR` |
| multiple | `MOVEM` **into** registers, both sizes, all modes |

### What falls back, and why

Every encoding not in the table above ends the block with a terminator and is
executed by the interpreter, which is why the harness compares the fallback as
carefully as it compares a block. **Five** separate reasons, and only the first
is a gap:

1. **Not written yet.** `MULU`, `MULS`, `DIVU`, `DIVS` (their cycle counts come
   out of the microcode's loop shape — `exec::divu_cycles` — which is a helper
   call rather than a lowering); `ABCD`, `SBCD`, `NBCD`; `TAS`; `MOVEP`; `CHK`;
   and every privileged or exception-raising encoding: `TRAP`, `TRAPV`, `RTE`,
   `RTR`, `STOP`, `RESET`, `MOVE to SR`, `MOVE USP`, `ILLEGAL`, the A line and
   the F line.
2. **Restartability.** See below.
3. **A charge that would have to be conditional.** `ir::Opcode::CHARGE` carries
   an *immediate*, so a cycle count that depends on a run-time value cannot be
   emitted. Where the paths that differ also *leave* the block, that is no
   obstacle and the frontend emits one exit per path with its own charges —
   which is what `Bcc` and `DBcc` do. Where they rejoin, the encoding is
   declined:

   | Declined | The run-time value the count turns on |
   | --- | --- |
   | a shift or rotate by a **register** count | two cycles per bit, and six different per-bit flag rules besides (`exec::shift`) |
   | `Scc Dn` on any condition but `ST`/`SF` | "two extra cycles when the byte is set, which is the one place a 68000's timing depends on a condition" (MC68000UM Table 8-11) |
   | `BSET`/`BCLR`/`BCHG` with a **dynamic** bit number into a data register | "a long bit operation on a register costs two more" (Table 8-7) — and which applies turns on whether the *reduced* bit number is at least sixteen |

   The memory forms of the last two are lifted, because a byte operand's
   reduction and a memory `Scc` cost the same either way.
4. **Another processor.** Only a 68000 is lifted. `lift` refuses any other
   model outright and `from_props` refuses the *configuration*, with a message,
   rather than silently interpreting: a 68010's shorter `CLR`, a 68020's
   per-instruction timing table, its misaligned operands and its full-format
   extension words are each a different lowering.
5. **The core is not in a liftable state**: a pending reset, a halt, `STOP`, an
   `RTE` replay in flight, **T** set in `SR`, an odd program counter, or a
   pending interrupt.

### The restartability rule, as the encodings it costs

A 68000's mid-instruction fault is architecturally visible in registers the
instruction has *already* changed — `MOVE.W (A0)+,(A1)+` whose write faults
leaves `A0` advanced — and in a group-0 frame whose program counter depends on
how far the prefetch got. The IR's only channel from a block to guest state is
`InsnStart::live`, a mapping taken **at a boundary**, so a write that lands
*between* boundaries cannot be expressed; `Opcode::GET_SLOT` says so in as many
words ("there is no `set_slot`").

So the engine does not reconstruct the fault. It unwinds every tick the partial
instruction charged and hands that **one** instruction to the interpreter, which
redoes it and faults where the hardware does. That is exact only while nothing
the instruction did beforehand can be seen twice: a register update cannot (the
boundary published it un-updated and the interpreter recomputes it), a
**committed store** can. So an instruction that commits more than one store is
not lifted, and on a 16-bit data bus a long store is two of them:

| Declined | Because |
| --- | --- |
| `JSR`, `BSR`, `PEA`, `LINK` | each pushes a long — two word stores |
| `MOVE.L <ea>,<mem>` and `MOVE.L <ea>,-(An)` | a long memory destination |
| `ADD.L`/`SUB.L`/`AND.L`/`OR.L`/`EOR.L`/`CLR.L`/`NOT.L`/`NEG.L`/`NEGX.L` into memory | the same |
| `ADDX.L`/`SUBX.L -(Ay),-(Ax)` | two word stores with the prefetch between them |
| `MOVEM` **to** memory | one store per register |

`Lifter::write_bus` asserts the budget in a debug build and `engine`'s host
asserts it again, so an encoding that got through `classify` names itself rather
than producing a wrong fault at run time.

**What that costs on real code was then measured**, and the paragraph that used
to stand here — that `JSR`/`RTS` pairs are common enough in 68000 code for a
second pass to weigh a `set_slot` opcode again — was wrong about which
encodings the bill is made of. *The lift rate, measured* below has the numbers
and the second pass's answer.

### The lift rate, measured

The differential sweeps say the two engines agree. They say **nothing** about
how much of a run the translated one carried: a frontend that lifted nothing
at all would pass every one of them, because a fallback agrees with the
interpreter by construction. So `M68k::jit_stats` grew the columns that answer
it, `M68k::jit_declines` grew a histogram that accounts for **every** fallback,
`rsemu run --trace cpu` prints both, and `tests/m68k_lift_rate.rs` measures
them on the boards in this tree that run a 68000.

**The call sites are a rounding error.** `JSR`, `BSR`, `PEA` and `LINK`

restriction's real bill is the graphics and block-move primitives: a long

rule and the wrong instructions.

#### And the second pass's answer on `set_slot`: not yet, and not one opcode

Three measurements decided it.

* **The coverage is not bad.** 93.8 % and 92.3 % of a real ROM's executed
  instructions run inside a block, which is the same order as the frontends
  already in this tree — `docs/platforms/pc64.md`'s x86 number is 97.3 % over
  nine hundred guest seconds.
* **The fallback was not a cost when this was first measured; it is now.**
  Twelve virtual seconds of the Macintosh Plus ROM took 1 620 ms on the
  interpreter and 4 121 ms on the translated engine, so lifting *more* would
  have made the board slower. The engine has since moved onto
  `jit::Dispatcher` and the arithmetic has inverted: the same twelve seconds
  are **1 430 ms** on `jit-host` against 1 622 ms interpreted, and every guest
  instruction that falls back now costs more than one that does not. *Where
  the time goes* below has the ladder. The restriction that produces those
  fallbacks is still the right one — see the next bullet — but the argument
  from speed for keeping it is gone.
* **`set_slot` alone would not remove the restriction.** The claim that one
  opcode would is too optimistic, and the reason is in this file already: a
  block cannot deliver the group-0 frame itself, because exception processing
  is not in the lifted subset, and the frame's program counter depends on
  `pc` moving once per prefetch slide *within* an instruction, which `lift.rs`
  deliberately does not model. So the fault still has to reach `exec.rs`, and
  `exec.rs` has one entry — re-run the instruction — which is exactly what
  re-commits the first store. Removing the restriction means switching this
  core from **restart** to **resume**: `set_slot` to publish partial registers,
  *plus* intra-instruction `pc` in the lifter, *plus* an entry point into the
  interpreter that delivers a fault from supplied state rather than by
  re-running. The third of those is a change to the oracle, and
  `ROADMAP.md` §9 makes restart-versus-resume a per-architecture policy rather
  than a frontend's choice. That is a design decision, not a commit.

So the restriction stays, and the ledger below keeps its one entry. What
changed is that the list of encodings it costs is now a measurement instead of
a guess.

### Where the time goes, and which of three suspects was the thief

`benches/m68k_mac_boot.rs` is the stopwatch and callgrind is the attribution.
Twelve virtual seconds of each ROM, best of six, release, on one x86-64 host
shared with other work (load average 9.5 to 13.3 across the run), every rep
hashing to the same `Machine::state_hash` as the interpreter:

| | `interp` | `jit` | `jit-host` |
| --- | ---: | ---: | ---: |
| `mac-plus` | 1 622 ms | 3 913 ms (0.41x) | **1 430 ms (1.13x)** |
| `mac-classic` | 813 ms | 3 170 ms (0.26x) | **659 ms (1.23x)** |

`jit-host` is the engine to read. `jit` is the portable backend, and on this
core it is *slower than the interpreter by a factor of two and a half*, which
is not a defect and is worth stating plainly: this frontend emits **51 IR ops
per guest instruction** — it performs its fetches and it computes every
condition-code bit — and `ir::Interp` spends about 190 host instructions on
each one, against an interpreter that does the whole instruction in about
2 400. No amount of caching closes that; only a code generator does.

That is the correction to a guess this file used to carry. Three costs were
named — no host code generator, no block chaining, and re-reading every word a
block was lifted from on every dispatch — and the obvious suspect was
**chaining**, because a 68000 block is 2.38 guest instructions and a dispatch
round trip is amortised over almost nothing. Under callgrind, on one virtual
second of the Plus ROM with the engine as it then was:

| | host instructions | share |
| --- | ---: | ---: |
| executing the IR (`Interp::step`, `Interp::set`, the loop over them) | 6.33 G | **71.3 %** |
| the scheduler and the devices | 0.80 G | 9.0 % |
| the address space, under a block's own accesses | 0.72 G | 8.1 % |
| the interpreter, on what the subset declines | 0.35 G | 3.9 % |
| **the cache lookup, the dispatch and `Host` setup** | **0.21 G** | **2.4 %** |
| **re-validating a block's words on every dispatch** | **0.10 G** | **1.2 %** |

Chaining and validation together are 3.6 % of the run, and the `jit` column
above is what removing both is worth: 4 222 ms to 3 913 ms, −7.3 %, still
2.4x slower than the interpreter. **The executor was the whole of it.**

After the move, the same virtual second is 2.30 G host instructions against the
interpreter's 2.385 G — and 0.92 G of each is `Scheduler::close_round`,
identical in all three engines, because a compact Macintosh is a board with a
60 Hz tick chain, a video circuit and two VIAs on it. **Half of what is left of
this workload is not the processor**, which is why 1.13x on the wall clock is
what a 2.9x cut in the CPU's own instruction count buys.

What is left to aim at has moved with the cut. Inside the CPU's half:

| | host instructions | share of the CPU |
| --- | ---: | ---: |
| `AddressSpace::read`, under `load_thunk` | 0.406 G | **41 %** |
| the code `jit::x86` generated | ~0.32 G | 33 % |
| the interpreter, on what the subset declines | 0.098 G | 10 % |
| `Chain::step` — the boundary work a link still pays | 0.106 G | 11 % |

`ROADMAP.md` §9.1's **first** mechanism is the software TLB and this core does
not have one: every guest access, including the two instruction fetches this
frontend performs per instruction, walks the address space. That is the next
measurement, and `FastMem` on `engine`'s `Host` is where it attaches. It is
also the one place where the Macintosh boards fight back — the glue's ROM
overlay is a *rebasable* alias, which `jit::Tlb::fill` refuses to cache at all
— so what it is worth here has to be measured rather than assumed from another
core.

### What is unusual about this frontend

* **Its instruction fetches are performed, not merely charged.** The other
  three frontends charge a fetch's ticks and never make the access. This one
  emits an `ir::Opcode::LD` with `AccessKind::Fetch` wherever `exec.rs` slides
  or refills the prefetch queue, because a 68000's fetches are ordinary bus
  cycles interleaved with its operand cycles, because **a fetch from an odd
  address is an address error** and a `JMP (A0)` or `RTS` to an odd target
  takes it at the refill — a run-time value no lift-time check could have
  declined — and because the words come back as values.
* **The prefetch queue has slots.** `PREFETCH0` and `PREFETCH1` hold what the
  block's own fetches returned, so the queue is modelled rather than
  re-derived at block exit. It is the column no other core in this tree has.
* **Every bus cycle charges itself through the host.** `Opcode::CHARGE` carries
  the microcode idle cycles alone. `InsnStart::ticks` is the static column and
  the two add up, which the harness checks.
* **A conditional branch is two exits, `DBcc` three**, emitted in increasing
  static-tick order because the verifier refuses a boundary whose retired ticks
  went backwards. `DBcc`'s counter is computed unconditionally and each exit's
  live map names either the old temporary or the new one, which is how the path
  that must *not* write `Dn` avoids writing it.
* **Self-modifying code** is answered three times: every store is recorded by
  guest-physical 4 KiB page and drained against the block cache at the next
  block boundary, by `jit::StoreLog` for a store a block made and by
  `Exec::wrote` for one an interpreted instruction made; a store into the
  *running* block's own window makes the block leave at the next guest
  instruction boundary, which is where the effect can first be honoured; and
  the block's first two words come out of the **prefetch queue** rather than
  out of memory at all, because a 68000 has already fetched them. The third is
  the one that was missing — see below. A 68000 has no instruction cache and no
  `FENCE.I`, so unlike `cpu::riscv` the middle one is not optional: coherency
  is architectural but for the queue.

### The two-word skew, which is where the one real bug was

A 68000 fetches **two words ahead**, so the instruction at a block's entry PC
is the word already in `prefetch[0]` — not whatever is at that address now. A
store that landed on it since is not seen by the instruction that consumes it,
and there is no way back. The engine lifted from memory and therefore executed
the store's result where the interpreter executed what it had already fetched.

A generated case found it, and it is the argument for reporting a rate rather
than a verdict: the committed sweep of 6 000 programs was green, and widening
it to 60 000 was not.

```text
  001000: 55cf  DBCS D7,$00100e
  001004: 47fb  LEA $b(PC,D3.w),A3
  001008: 59f8  SVS $00001ff5.w
  00100c: e1e4  ASL -(A4)
  00100e: 991b  SUB.B D4,(A3)+
  001010: 8f1b  OR.B D7,(A3)+      ; A3 = $001012 — two bytes ahead
  001012: 62f6  BHI $00100a
```

`OR.B` writes onto the word `BHI` is fetched from. The hardware runs the `BHI`
it already had; a block lifted from memory ran whatever the stored byte made of
it — twenty cycles against twenty-two, and a different instruction. The fix is
that the lifter's source answers the entry PC and the word after it out of
`State::prefetch` and everything from `pc + 4` on out of memory, and a cached
entry is **keyed** on the queue it was lifted with, so a core whose queue has
moved on misses rather than being served the wrong translation.

Recording the queue was enough while a cache hit re-read the bytes it was
lifted from; under a store filter it is not, and the case is worth writing out
because it is the one the obvious design gets wrong. A store rewrites the word
at a block's entry; the filter drops the block; the block is lifted again from
the queue the guest had *then*, which is the pre-store word, and cached. Later
control reaches that PC again, this time with the *new* word in the queue — and
nothing has stored since, so the filter has nothing to say. `cache_key` puts
both queue words beside the model for exactly that.

### Known failures

The ledger only ever shrinks (CLAUDE.md, *CPU cores*). It has one entry.

| # | What | Status |
| --- | --- | --- |
| 1 | **A second bus master writing an extension word a block has already lifted.** The queue's two words are read from the queue, but an *extension* word further ahead than it reaches is baked in as a constant at lift time. The guest's own stores cannot reach that: the window guard ends the block at the store, and an instruction's own fetches precede its own store. So it needs DMA or a second processor writing the code a block is running. | Open, and not reachable by any board in the tree: `m68k-mini` has one master. |

Everything else the harness reaches agrees. `cpu-m68k-lift` adds no
dependencies and is `no_std + alloc`; `jit`, which the two translated engines
also need, adds none either, and only `jit-x86` and `jit-arm64` — the host code
generators `jit-host` reaches through — imply `std`.

### The rates

Measured by `tests/m68k_lift_differential.rs`, which is where a long run
belongs; `differential`'s own tests take a strided slice so `cargo test` stays
quick.

Every sweep runs on **both** translated engines, because `jit-host` is not a
different engine from `jit` but a different *mix*: a block its code generator
refuses runs on the portable backend beside it. So each row below is two runs,
and the case count is per engine.

| Sweep | Cases per engine | Disagreements |
| --- | ---: | ---: |
| every sixteen-bit opcode word, `$0010 $0000 $2400` extension words | 65 536 | 0 |
| every sixteen-bit opcode word, `$f80c $ffff $fffe` extension words | 65 536 | 0 |
| every sixteen-bit opcode word, **user state** | 65 536 | 0 |
| seeded pseudo-random six-instruction programs, eight seeds | 6 000 | 0 |
| **a real Macintosh Plus ROM**, twelve virtual seconds, whole-machine state hash every second | 12 | 0 |
| **a real Macintosh Classic ROM**, the same | 12 | 0 |

The last two are `tests/m68k_lift_rate.rs`, behind `RSEMU_MAC_ROM_DIR`, and
they are a different *kind* of case from everything above them: twelve
checkpoints rather than twelve cases, but each one is a hash of the whole
board — every register, every byte of RAM, every device — after **eight and a
half million guest instructions of somebody else's real code**. A generated
program exercises encodings; a ROM exercises the sequences a compiler and a
hand-written operating system actually emit, and it is the only corpus here
that does.

Two wider runs were made by hand at the commit that landed this, over the same
committed harness, and are recorded because they are what the ledger above
rests on rather than because they run on every commit: **524 288** opcode-word
cases — four extension-word sets crossed with both privilege states — and
**400 000** generated ten-instruction programs over two hundred seeds. Zero
disagreements in both. The second of those is the run that found the
prefetch-queue bug above at 60 000.

The opcode sweeps are the corpus this core has and the other three frontends do
not: a 68000 opcode is sixteen bits, so "every encoding there is" is 65 536
cases rather than an intractable space. Nothing is skipped — an encoding the
frontend declines is still compared, because the fallback has to leave the
guest where a block would have, and an illegal one is compared through its
exception.

## Not to be read

Every copyleft 68000 implementation: Musashi-derived code inside GPL projects,
UAE and WinUAE's CPU cores, Hatari, vAmiga, MAME's `m68k`, QEMU's `m68k`
target, Unicorn, and anything derived from them (CLAUDE.md, *Provenance*). The
same for the floating-point side: the 68040 floating-point software package's
assembly — which is the *only* published description of some of what Section
9 leaves to software, and is exactly why the frame layouts here were read off
Figure 9-10 and Table 9-16 instead — any `softfloat` under a copyleft licence,
and the transcendental kernels inside GPL emulators. The manuals above describe everything this core
does, and the transcendental algorithms here are textbook mathematics — Taylor
series, the `atanh` form of the logarithm, the half-angle arc tangent, and
Payne and Hanek's reduction (*SIGNUM Newsletter* 18(1), 1983) — computed
against GNU `bc`, which is a program run rather than a source read.
