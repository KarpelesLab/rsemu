# Known failures: AccuracyCoin (125 whole-machine tests, MIT, (c) 2025 Chris Siebert).
#
# Keyed by the low byte of the test's result address rather than by name: the
# address is what the ROM writes and is stable across releases, whereas the
# display name is text on a menu. tests/conformance/accuracycoin_tests.rs has
# the mapping, and the runner prints both.
#
#   4d                # $044D, "PC Wraparound"
#
# The `# why` note is mandatory, and this file only ever shrinks.
#
# Two caveats worth knowing before anything is written down here:
#
#   * The ROM targets an RP2A03G CPU and an RP2C02G PPU. A handful of tests
#     legitimately behave differently on other revisions — a divergence must be
#     traced to a documented revision difference before it is excused, not
#     assumed to be one.
#   * The five "DRAW" pages assert nothing and are excluded by the runner, so
#     they can never appear here.
#
# ---------------------------------------------------------------------------
# Measured 2026-08-31 against the pinned ROM: 130 of 141 pass, 11 fail.
# ---------------------------------------------------------------------------
#
# The earlier "81 of 125" was measured through a stale copy of the ROM's
# `TestPages:` table. The pinned ROM carries 146 menu entries — 141 that assert
# and 5 DRAW pages sharing `result_DrawTest` — and the old table named three
# addresses ($0402, $0418, $0464) that ROM never writes while omitting nineteen
# tests it does run. `accuracycoin_tests.rs` has been regenerated from the ROM;
# of the nineteen recovered tests four already pass and fifteen are below.
#
# Every entry below names a subsystem rsemu has not built yet, and each one is
# traced to the specific error code the ROM reported and the line in the ROM's
# own README that explains it. There are no "fails and I do not know why"
# entries; if one appears, it is a bug and not a ledger line.
#
# Five causes account for all 44:
#
#   A. [FIXED] No /RDY on cpu.mos6502. `core::device::CycleGate` is the seam;
#      `nes.oamdma` is now the RP2A03's whole DMA unit and drives it, so a
#      sprite copy really halts the core for 513 or 514 cycles and the halt and
#      alignment cycles repeat the core's own read on the bus where devices can
#      see it. That alone closed ten tests, four of them on the sprite page:
#      every "Clockslide" the ROM writes is calibrated against the stall.
#   B. DMC DMA exists now — the same unit runs it, on the halt/dummy/alignment
#      /get shape the wiki documents — but its *phase* is not right yet: the
#      ROM reports "the DMA occurred on the wrong CPU cycle" rather than "there
#      is no DMA", which is a different and much smaller problem.
#   C. [FIXED] No CPU-side open-bus data latch. `unassigned = open-bus` really
#      is open bus now: `MemAttrs::bus` carries the master's last driven byte,
#      the space answers an unmapped read with it, and `$4014`, `$4016`/`$4017`
#      and `$4000`-`$4013` take their undriven bits from it rather than from a
#      constant. `$4015` is marked `internal()`, so reading it leaves the latch
#      alone. What is left of (C) is only what needs a DMA to observe it.
#   D. [MOSTLY FIXED] PPU staleness is scanline-exact, not dot-exact (ROADMAP.md 4.2's one
#      remaining phase-3 item).
#   E. APU frame-counter and length-counter edges are not on the right CPU
#      cycle, and neither the APU nor the ports can see get/put phase.
#
# Since that measurement `core::sched` grew `TickCursor`: a runnable publishes
# its own tick counter as it executes, and catch-up aims at the cycle an access
# really happened on rather than at the start of the quantum. That closed the
# APU's length-counter tests and half of (D) on its own.
#
# ---------------------------------------------------------------------------
# A. The CPU has no /RDY line, so nothing can halt it
# ---------------------------------------------------------------------------
#
# nes.oamdma performs the whole transfer correctly and records the 513 cycles
# it should have stalled for (`OamDma::stall_owed`), but cpu.mos6502 has no pin
# and no hook to be handed them. src/dev/nes/dma.rs names the two shapes the
# seam could take. Everything here is that one missing line.


# ---------------------------------------------------------------------------
# B. No DMC DMA
# ---------------------------------------------------------------------------
#
# The APU models the DMC channel but not its sample fetch, which on hardware is
# a DMA that steals CPU cycles — so it needs (A) before it can exist at all.
# Every test on the ROM's "APU Registers and DMA tests" page is about where that
# fetch lands relative to a CPU access, so all of them report the same thing.

77                # $0477 "DMC DMA + OAM DMA" code 1: DMC DMA timing. There is
                  # no DMC DMA to overlap the OAM one with.
78                # $0478 "Implicit DMA Abort" code 1: as above.
5c                # $045C "APU Register Activation" code 1: the ROM says
                  # outright that a series of prerequisites failed — CPU and PPU
                  # open bus, DMA + Open Bus, DMA + $2007 Read. Cascades from
                  # (B) and (C); nothing of its own.

# ---------------------------------------------------------------------------
# C. No CPU-side open-bus data latch
# ---------------------------------------------------------------------------
#
# The address space has an open-bus policy per space (`unassigned = open-bus`),
# which is what makes an unmapped address answer. What is missing is the *CPU's*
# side: a 6502 leaves the last byte it drove on the data bus, and a read of a
# write-only register returns that byte rather than anything the device chose.
# That latch belongs in cpu.mos6502, beside the cycle accounting.


# ---------------------------------------------------------------------------
# D. PPU staleness is scanline-exact, not dot-exact
# ---------------------------------------------------------------------------
#
# ROADMAP.md 4.2 names this as the one thing left in phase 3: the run loop stops
# the CPU at the PPU's next *event*, which puts the vblank flag and the NMI on
# the right scanline but not always on the right dot. Every test below reports
# a flag set or cleared on the wrong PPU cycle, which is exactly that.

55                # $0455 "NMI at VBlank end" code 1: the NMI was disabled too
                  # early or occurred too late.

# ---------------------------------------------------------------------------
# D2. PPU sprite-evaluation quirks not modelled
# ---------------------------------------------------------------------------
#
# Not timing: these are behaviours of the two-phase sprite evaluation and of
# $2004 that the engine does not implement yet. Each is a piece of work in
# src/dev/ppu, not a seam.


# ---------------------------------------------------------------------------
# E. APU frame counter, and get/put phase
# ---------------------------------------------------------------------------
#
# The frame counter's four edges are not placed on exact CPU cycles — `nes.apu`
# reports `next_event_tick() == None` for precisely this reason — and neither
# the APU nor the controller ports can see whether an access lands on a "get" or
# a "put" cycle, because a device is handed a bus access, not a CPU half-cycle.

6a                # $046A "Delta Modulation Channel" code 1: $4015 bit 4 must
                  # follow a playing sample. See (B) — there is no sample fetch.
